## 现状速览

```
数据链：sync-dingtalk / sync-wdt（受限只读网关 → raw_dingtalk/raw_wdt/raw_manual）
   → roll-manifest（WDT 窗口每日滚动）→ extract-mart（raw → mart_ops.fact_*/dim_*）
   → 消费端：bi_web（FastAPI，只读+Redis 缓存）/ daily_robot.mart_cli（写 robot_outbox）
   → dingtalk-gateway 轮询 outbox 投递钉钉；pages-* 每日生成榜单 HTML 由 nginx 直出
调度：scheduler 长驻容器，30s 轮询 Nacos(PIPELINES/REGIONS) + 种子兜底，croniter 触发，
      subprocess 拉起 CLI，MySQL named lock 防重
前端：frontend/bi-react（React18+Vite5+TS5.5 严格模式），后端卡片驱动，echarts
测试：unittest 64+ 单测文件 + 5 个集成测试（docker mysql8.4+redis7）+ GitHub Actions CI 三 job
部署：docker-compose.integration.yml（15 服务 profiles）+ lan 覆盖层 + 云上 /opt/dops 本地编排
```

底子不错：凭据零入库、APP_ENV 库名铁律、幂等 upsert、迁移 checksum 冻结、前端类型严格、CI 强制 `--build`。以下问题集中在**新旧双轨未收敛、重复口径散落、大文件膨胀、可观测性缺失**四个方向。

### 1.4 工程纪律补差

- **类型标注**：新模块齐全，老模块全缺（`common/broadcaster.py:22`、`common/daily_robot/core.py:34`、`listener.py:22`）；`core.py:14-17` 运行时 `sys.path.insert` 应改包结构导入。老模块随双轨退役一并清理，存量按 pyright 逐步收紧。
- **静默失败**：`pipeline_config.py:194-197/261-263`、`region_config.py:196-197` 的 `except Exception: pass/None` 无日志——fail-open 设计可保留，但必须加结构化 warning（含 namespace/group/dataId），否则注册表故障不可观测。
- **CLI 错误纪律**：`cli.py:520-607` 全部 `except Exception → exit(1)` 不打 traceback。建议：`--debug` 环境变量开关打印 traceback，run 状态表落 `error_class` 字段，排障成本立降。
- **raw 写入性能**：`raw_repository.py:127-138` 逐行 `cursor.execute` upsert，而 extract 侧已批量 `executemany`（`extract_mart.py:375`）。raw 层补齐批量写入，大数据集同步提速明显。
- **`%%` 双写约定**：pymysql 下 LIKE 字面量逃逸靠人肉（`queries.py` 静态 `'%合计%'` 与参数化 `'%%合计%%'` 混排）。引入 SQL 片段构造器统一处理，或全量改参数化 LIKE（`LIKE CONCAT('%%', %s, '%%')`）。

## 二、架构优化方案

### 2.1 收敛运行路径（切换收口）

当前处在新旧双轨窗口期：`listener/report_intake`、`broadcaster/gateway`、`daily_robot.core/mart_tasks` 并存，口径双写风险仍在。**行动**：以 `docs/阶段4切换运行手册.md` + checklist 为依据定切换日，切流顺序建议 机器人出口 → 报数入口 → 旧 core 退役，每步留 digest 比对回退位。

### 2.2 调度：从"各自 cron"到依赖编排

- 隐患实锤：`roll-manifest` 必须先于 `sync-wdt`，否则幂等重拉整天（`cli.py:544-549`）；sync 02/07/14/16 → extract 04/08/15/17 靠时刻表错位维系。
- 方案：scheduler 引入轻量 DAG——管道声明 `depends_on`，触发条件 = cron 到点 AND 上游当日 run 成功。不必上 Airflow，MySQL 里查 `sync_runs` 状态即可实现，改动集中在 `scheduler.py`。
- 顺带把 `_COMMAND_TABLE` 模板化（见 1.1-A3），service_id 与命令解耦后 Nacos 发布面更小。

### 2.3 配置与控制面

- **fail-open 加固**：Nacos 不可达时用上次配置放行是合理的，但"关停某条线"在抖动期不生效。给关键开关加 `fail_closed` 白名单（如 outbox 投递类），其余保持 fail-open + 告警。
- **编排文件收敛**：仓库内 `docker-compose.integration.yml` / `lan` / `ntp-cloud` 三份 + 云上服务器本地 `/opt/dops/docker-compose.dops.yml` + nginx pages.conf 游离在 git 外（记忆：已计划"随 B4 收口走 PR"）。**行动**：云上编排与 nginx 配置纳入仓库 `docker/cloud/`，服务器侧只放 env/凭据，git pull + compose up 成为唯一发布动作——同时根治"docker compose restart 不应用 env_file"这类操作事故。
- **README 更新**：`数字化/` 目录结构描述为历史残留，按 `common/` 实际分层重写。

### 2.4 时钟统一（B6 既定事项提前）

extract 侧 `synced_at` 固定 UTC + 业务日 +08:00 换算（`extract_channel_ops.py:85-100`，09-23 已出过"数据截至"整天错位事故），bi_web 侧用 MySQL `CURDATE()`（`queries.py:52-54`）——两套时钟并存。**行动**：全链路定死"存储 UTC、展示 +08:00"，BI 查询的业务日过滤统一走 `calendar_utils` 的换算函数，消灭裸 `CURDATE()`。

### 2.5 可观测性补建

现状排障靠查 DB run 状态。最小成本补齐：① scheduler/gateway 输出结构化 JSON 日志（run_id/trace 贯穿 sync→extract→outbox→delivery）；② 关键指标落表或暴露 `/metrics`（管道成功率、outbox 积压、卡片缓存命中率）；③ Nacos 读取失败、fail-open 触发、整集 digest 跳过三类事件必告警。

### 2.6 前端

结构已健康（后端卡片驱动、七类卡片原语、`useCube` 共享缓存、vendor 拆包 gzip ~10KB）。仅两项：设计系统双份漂移收口（1.1-A5）；补 1-2 条 Playwright 冒烟 E2E（驾驶舱首屏卡片渲染 + 区域下钻跳转），防止后端契约变更静默破页。

## 三、数据中台优化方案

### 3.1 口径治理（数据中台的头号风险）

- **「合计」汇总行排除散落 19+ 处**（`bi_web/queries.py:61,75,90,101…`），源表出现"总计/小计"新变体即全量翻倍。**行动**：extract 层增加 `is_summary_row` 标记列（AI 表 melt 时按标题正则打标一次），查询侧改为 `WHERE is_summary_row = 0`——口径从"19 处 LIKE"收敛为"1 处打标"。
- **region 真源唯一化**（见 1.3-C1）：当前代码/种子/Nacos 三处并存，新区域上线改代码是数仓层最不该有的操作。
- **月目标口径** `Σ(每人 MAX(monthly_target))` 等已验证口径从 `offline_summary.py` 提升到 `common/metrics/` 共享层注册，BI 与机器人共用同一函数，杜绝口径漂移。

### 3.2 水位与增量一致性

- 增量窗口用 `synced_at`（同步时间）是正确取舍（`extract_mart.py:66-69` 注释已说明），但重跑/补拉易漏边界。**行动**：run 记录增加 `watermark_from/watermark_to` 显式字段，重跑默认继承上次水位而非按当前时间推算；`full_rebuild` 路径保留但加 dry-run 预估行数。
- `receiver_area_norm`（v3 迁移补列）这类回填型变更，沉淀一个标准"迁移+回填"二段模板，避免每次手写。

### 3.3 迁移治理

`live_migrations` 已 26 个版本且持续增长，checksum 冻结纪律正确但 `_apply_to_connection`（`:406-417`）对 cursor 返回值 dict/tuple 双形态猜测较脆。**行动**：统一 `cursorclass=DictCursor`；每季度归档只读历史版本（折叠为基线 schema + 增量），控制版本表膨胀；保留 checksum 冻结不变。

### 3.4 数据质量与验收

- 现有 `record_id_digest` 双跑一致验收很好，**推广到 mart 层**：extract 每 run 落 `fact 行数 + SUM(金额) 哈希`，双跑比对即刻发现口径回归（09-23 RDS 拉平时正是靠此法验证 9,447→129,717 行）。
- `queries.py` 已带 `as_of+stale` 过期标记，推广到所有面板接口并在前端卡片角标透出"数据截至"，让业务方自解释。
- 备份表生命周期：`*_bak_20260923` 6 张 RDS 备份表已计划观察 1 周后 DROP——把"CTAS 备份→观察→DROP"固化为 runbook 模板（含自动到期提醒）。

### 3.5 性能与容量

- raw 层批量写入（1.4）。
- `db-大表排查报告-2026-09-17.md` / `db-大表治理手册-2026-09-17.md` 已有治理基线，按手册推进索引/分区/归档即可；重点盯 `wdt_records`（12.9 万行起步，日增）与 outbox。
- Redis（华为云 DCS 已交付但无消费方上云）：bi-web 上云是唯一前置；落地时沿用 fail-open 缓存层设计，缓存键带 `as_of` 版本号，避免口径变更后脏读。

### 3.6 待办收口（顺带完成）

- 李树军从 shaoxing 板块拆出单列 → 走 1.3-C3 板块配置表方案。
