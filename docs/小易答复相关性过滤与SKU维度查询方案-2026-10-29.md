# 小易答复质量改造方案：理解增强、相关性过滤、SKU 维度查询、数据缓存

- 日期：2026-10-29（v3，补数据缓存层设计）
- 触发：客服群反馈（2026-10-29 17:27 截图）三类问题：
  1. **理解问题**：问某店 9 月销售及同比，答复按店铺口径作答并回显「同比：0 条」——问句实际要 SKU 粒度，且同比基期早于数据起点；
  2. **不相关内容**：「回复上，如果不相关的内容可以不输出吗」——答复混入「⚠️ 两点特别说明」长解释段、其它店铺「供参考」逐店清单、`has_previous_data=false` 内部字段名；
  3. **维度缺失**：「按照 SKU 维度没开发」——已对外承诺下月初解决（节点 2026-11-03 当周）。

## 1. 现状与根因

### 1.1 答复链路

群消息与 Web 问答**共用同一出口**：`common/kb_web/service.py:124` 复用 `common/kb_qa/app.py` 的 `_answer()` → 规则意图路由（`router.py classify`）/ multi 拆分 / 工具 agent（`_try_agent` → `agent.py run_agent`，function calling）→ 自由文本**原文直发**，出口无任何门禁。规则模板通路（商品参数卡、澄清卡、号码卡）为模板渲染，不在本次问题面内。

### 1.2 根因分层

| 层 | 根因 | 位置 |
| --- | --- | --- |
| 理解层 | 无实体/期间/粒度解析：SKU 粒度问句被按店铺口径作答且不自知；期间早于数据起点（订单数据 2026-08-22 起）时照跑工具，同比基期必然缺数 | `router.py` 仅词表分类；无期间/实体结构 |
| 工具层 | `channel_yoy` 把全部店铺行（最多 50 行）喂给 LLM，模型顺手列出「其它店铺供参考」 | `agent.py:654-792`（`rows[:50]`） |
| 生成层 | system prompt 要求「has_previous_data=false 必须明示」，模型扩写成多行 ⚠️ 解释段并漏出字段名；无答复格式规范 | `agent.py:40-67` |
| 表示层 | 缺数渲染成「同比：0 条」（缺数 ≠ 0）；问句回显「问题：…」 | 模型自由发挥，无规范化 |
| 出口层 | agent / multi 渲染 / 手册问答三路自由文本均直发，无过滤 | `app.py:700-703、725-727、1003-1010、1130+` |

## 2. 总体设计

五层防线 + 一个横切缓存层 + 一个闭环，**确定性优先、LLM 兜底最后、全部 fail-open**：

```
L1 理解   实体/期间/粒度解析 + 数据边界注册表 → focus 结构 + 边界直答
L2 工具   聚焦压缩（只喂问句相关行）+ 新增 sku_sales / sku_inventory
L3 生成   prompt 答复纪律 + 答复格式规范（结论→数据→一句注释）
L4 出口   reply_filter：规则过滤 + 表示规范化 + 超阈值 LLM 裁切（observe/enforce）
横切     Redis 数据面：结果缓存 + 版本发布订阅失效 + 预暖 + 跨进程协同 + 开关分发 + 观测治理
L5 闭环   评测集离线回放 + audit/badcase 周报 + 分层配置开关 + 缓存 metrics
```

原则：群与 Web 同出口同过滤同缓存键空间；规则模板通路不过滤（防误伤）；缓存规范不新造、复用并上移既有实现；**Redis 定位从「各面自用 KV」升级为共享数据面（缓存/失效/协同/分发/观测），但每一角色独立 fail-open，主链路永不硬依赖 Redis 可用性**；本方案不建新表、不扩 DDL 列，回滚靠开关与 flags。

## 3. 方案 A：理解增强

**A1 实体/期间/粒度解析（focus 结构）**
在 agent 调用前增加轻量解析（规则优先：店铺/渠道/品牌名词典 + 期间正则含「9 月/上个月/本月/去年同期」；规则 miss 时复用现有 `_reparse_intent` 的 LLM 二次解析通道扩展字段）。产出 `focus = {stores[], channels[], skus[], period(start,end), yoy_period, granularity}`，四处共用：L2 聚焦压缩、L4 实体匹配删除、工具默认参数、**缓存键的期间类别判定**。解析失败 fail-open：focus=None，各层退化为现状行为。

**A2 数据边界注册表（boundary 直答）**
新增配置 `DATA_BOUNDS`：表 → `data_start`。初值上线前探针填充（`SELECT MIN(trade_time)/MIN(business_date)`）：`fact_order_line` = 2026-08-22（已知），其余探针实测。问句期间或同比基期 < data_start → **不跑工具不进缓存**，一句话直答：「同比基期 2025-09 早于订单数据起点 2026-08-22，无去年数据；本期数据如下…」或直接说明查不了。从根上消灭「同比：0 条」与缺数解释段。

**A3 不支持粒度的话术规范**
粒度不支持时（如品牌维度，见 C8 P2）限一句话：「目前支持 店铺/渠道/SKU 维度，品牌维度暂未开放，最接近的是 X」；禁止多行解释、禁止引导用户找其它团队导表。

**A4 低置信反问**
意图置信度低或粒度多义（「销售」未给维度且历史轮无锚点）→ 一句话反问（复用现有 clarify/pending 机制），不先答错再解释。

## 4. 方案 B：答复相关性过滤

**B1 工具层聚焦压缩（L2，确定性）**
- `channel_yoy` 增可选参数 `shop_name`；问句点名店铺时只回该店行。
- 通用聚焦：executor 依 `focus` 压缩喂 LLM 的 `rows` = 命中实体行 + TOP 3，其余压成 `others: {count, total_amount}`；`_export_rows`（快照/导出）保持全量不受影响（`agent.py:415-447`）。

**B2 Prompt 答复纪律 + 格式规范（L3）**
`_SYSTEM_PROMPT` 追加：
1. 只答被问到的对象与指标；未被索要的「其它店铺/供参考/顺便」数据一律不输出；
2. 答复格式：结论一句 → 数据（带日期与单位）→ 注释限一句放末尾；「必须明示缺数」改写为「一句话说明即可」；
3. 缺数一律表述为「无数据/—」，**禁止写成 0**；
4. 禁止内部字段名/协议词（`has_previous_data`、tool 名等）与「AI 回答说明/问题理解：」自解释标题。

**B3 出口过滤器 reply_filter（L4）**
新增 `common/kb_qa/reply_filter.py`，`filter_reply(question, reply, focus=None) -> reply`：
- 规则过滤（零成本先跑）：「⚠️/说明/注意」段超 2 行压缩为首句；「供参考」清单行内实体与 focus/问句实体无交集则删；问句回显行删除；
- 表示规范化（确定性改写）：snake_case 标识符掩蔽为口语；「0 条/0 元」与缺数语境共现改写为「无数据」；
- 长度门禁：过滤后仍 > 600 字且单意图 → 一次 LLM 裁切（temperature=0，「只删与问题无关段落，保留全部数字与结论」）；失败返回规则过滤结果（fail-open）；
- 挂载点：`_try_agent` 返回后（`app.py:700-703、725-727`）、multi 渲染出口（`app.py:1003-1010`）、手册问答出口（`_answer_docs`）；Web 通道因复用 `_answer` 自动覆盖；
- **observe/enforce 双态**：observe 24h 只算 diff 落日志不替换，抽检 10 条（M4）后切 enforce。

**B4 闭环**
过滤 diff（前后字数、删除段落摘要）落日志；`badcase.py` 周报增「过滤命中」聚类；每周人工抽检纳入值班清单。

## 5. 方案 C：SKU 维度查询

**C1 SKU 身份解析**
keyword → `kb_products`（`code/barcode_single/barcode_case/name` 精确→模糊）解析出 `spec_no/goods_name`；miss 回退 `fact_order_line.goods_name LIKE`；命中多 spec 列清单反问（复用 pending 机制），不猜不合并。解析索引进缓存（D2 维度字典）。

**C2 新工具 `sku_sales`（SKU 销售）**
- 源 `fact_order_line`，口径与 `channel_yoy` 同源（`paid_amount`，剔除取消/待付款/全额退款关闭）；强制 `trade_time` 日期过滤；
- 参数：`keyword`（可选）、`start_date/end_date`（缺省本月 1 日至今）、`channel`/`shop_name`（可选）、`top_n`（缺省 10）；
- 预定义 SQL + 占位符（延续「LLM 只选工具给参数」铁律）；返回合计销售额/件数 + TOP N（`goods_name/spec_no/quantity/paid_amount/占比`）；
- 趋势不另开工具：库存表 `qty_7days/qty_month` 已含近 7/30 天动销，随 `sku_inventory` 返回。

**C3 新工具 `sku_inventory`（SKU 库存）**
- 源 `fact_inventory_sku_daily` 最新 `business_date` 快照，跨 `warehouse_scope` 汇总 `available_qty`，在途单列 `purchase_intransit_qty`；快照读法复用 `common/broadcast/queries.py:87`；
- 参数：`keyword`（空 = 三态分布总览 + 各态 TOP 5）、`state`（`URGENT/OVERSOLD/DEAD`）；
- 返回含 `daily_avg/days_left/stock_state`，随结果带一句三态口径（DEAD=近 30 天出库为 0，与库存量无关）与**快照日期**（freshness 必带）；
- 快照全量行进缓存按 data_version 钉键（6.3），重复问库存零库查询。

**C4 白名单补表**
`_SQL_TABLES` 增 `fact_inventory_sku_daily` 口径注释（最新日快照、`warehouse_scope` 维度、三态定义、`days_left` 含义），组合问句（「有货但上月没动销的 SKU」）走 `query_sql` 可答。

**C5 导出与快照配套**
`sku_sales/sku_inventory` 登记进 `_capture_query_snapshot` 分支（`agent.py:415-447`）与 `query_export.py` 的 allowed_tools / `_columns_for` 列映射——群里「导出表格」对 SKU 结果同样可用；快照 `data_version` 取快照日期；**缓存命中时快照登记用命中 payload 的同一份 rows**（6.3），保证答复数字 = 导出数字 = 快照版本。

**C6 路由与权限**
- `router.py _SALES_WORDS` 增补：`SKU、单品、每个品、按品、各款、哪款、哪几个品、规格编码`；
- `_SYSTEM_PROMPT` 工具选择增补：「按单品/SKU 销售 → sku_sales；库存/可售天数/呆滞 → sku_inventory」；
- 权限：群通道全量开放（同 `daily_sales`）；Web 通道归入 `kb_web_acl` 业务白名单工具集（`allow_business=1` 才 offering）。

**C7 表示要求**
SKU 销售答复必带期间与口径一句；库存答复必带快照日期；多 spec 命中列编码不合并。

**C8 P2 预留（本次不做）**
品牌维度：`fact_order_line.brand_name` 已在白名单，后续给 `channel_yoy/sku_sales` 加 `group_by=brand` 即可；本次以 A3 话术规范约束解释长度。预聚合表 `agg_sku_daily` 同列 P2（见 6.9 触发线）。

## 6. 方案 D：Redis 数据面与缓存层

### 6.1 现状盘点：Redis 只被当「各面自用 KV」

已有四个角色：bi-web 卡片缓存（`biweb:card:*`）、kb_qa 对话上下文（`context.py`，2026-10-22 Redis 化）、kb_web 会话、qr_login。v2 方案只再叠一层工具结果缓存，仍是「各面自用」。缺的是把 Redis 当**数据面**用的六个能力：

1. **无版本发布与失效**：新鲜度靠 TTL 猜（热 300s），T+1 补录落地后缓存仍陈旧到 TTL 到期；各读方还各自 `MAX(business_date)` 探针；
2. **无跨进程协同**：kb-gateway 与 kb-web 是两个进程，进程内 per-key 锁互不生效，同一重聚合两边各算一次；
3. **无预暖**：每天首问必等实时聚合（`channel_yoy` 两期 GROUP BY）；
4. **无入口保护**：钉钉回调重试、问句风暴直接穿透到生产库与 LLM；
5. **开关生效要重启**：observe→enforce、单层回滚需逐进程重启；
6. **故障不可见**：fail-open 吞掉全部 Redis 异常，实例挂了无人知道（静默降级比降级本身危险）。

### 6.2 角色与键空间清单

| 角色 | 键前缀（结构 / TTL） | 写方 → 读方 | Redis 不可达时 |
| --- | --- | --- | --- |
| R1 工具结果缓存（冷/热/版本钉键，见 6.3） | `kbqa:tool:*`（string / 热 30min、冷 24h、版本钉 24h） | agent executor → 答复链 | miss 直查 |
| R2 query_sql 缓存 | `kbqa:sql:{sha1}`（string / 热 300s） | 同上 | miss 直查 |
| R3 维度字典（scopes/channels/channel_map/SKU 解析索引） | `kbqa:dim:{name}:{ver}`（string / 1h） | executor → executor | miss 直查 DISTINCT |
| R4 数据版本注册表 | `mart:ver:{table}`（hash：max_date/synced_at/run_id / 发布覆盖） | extract 管线 → 全部读方 | 回落 `MAX()` 探针（进程内 60s 缓存） |
| R5 失效总线 | `mart:invalidate`（pub/sub） | extract 管线 → gateway/Web 订阅者 | 漏失效由 TTL 兜底（双保险） |
| R6 开关分发 | `kbqa:flags`（hash）+ `kbqa:flags:pub`（pub/sub） | 运维/初始化自 config → 各进程热更 | 用文件 config 值 |
| R7 跨进程计数与 metrics | `kbqa:metric:{day}:{name}`（INCR / 48h） | 各进程 → 周报/诊断端点 | 仅本进程 metrics |
| R8 问句频次统计 | `kbqa:qfreq`（ZSET / 7d 滑动） | app.py → 预暖清单/评测集候选 | 用手置预暖清单 |
| R9 query embedding 缓存 | `kbqa:emb:{sha1(text)}`（string / 7d） | RAG 查询路径 | 现调 embedding API |
| R10 去重与限流 | `kbqa:dedup:{msg_id}`（SET NX / 1h）、`kbqa:rl:{uid}:{min}`（INCR / 60s） | app.py 入口 | DB 唯一键兜底 / 限流放行 |
| R11 进程心跳 | `kbqa:hb:{proc}`（string / 60s） | 各进程 → 监控/周报 | 靠 R7 error 计数暴露 |

既有键空间（`biweb:card:*`、kb_qa 对话、`kbweb:sess`、qr）不动，纳入 6.7 治理登记表。

### 6.3 核心机制：版本发布-订阅失效 + 分层缓存

**缓存分层**（冷热语义沿用 bi-web 规范，契约层纯移动至 `common/cache_core.py`）：
- 封闭期结果（窗口 end < 今天）→ 冷 24h，键带 end 月；
- 开放期结果（含今天）→ 热 **30min**（由 300s 放宽：失效改为事件驱动后 TTL 只是兜底，见下）；
- 库存快照 → 按 `latest business_date` 版本钉键 24h，快照重写键自然翻转；
- query_sql → 只热 300s（自由 SQL 期间难判定）；参数规范化复用 `normalize_params`；只缓存成功结果；**LLM 答案不缓存**。

**发布-订阅失效**（把陈旧窗口从 TTL 猜变成事件驱动）：
1. extract 管线（mart extract / 渠道 T+1 采集 / 库存快照重写）落库成功后：`SET mart:ver:{table}` + `PUBLISH mart:invalidate {table, version}`；
2. 订阅者（kb-gateway、kb-web）收消息后：更新进程内版本视图；按写缓存时登记的开放期键清单（`kbqa:open:{tool}` set，写时 SADD、失效时 SUNION+DEL 后清空，**不用 SCAN**）purge 受影响热键；版本钉键不处理（自然轮换）；
3. freshness 话术与版本钉键统一读 R4（进程内 60s 缓存），R4 缺时回落 `MAX()` 探针（现状行为）；
4. **双保险**：pub/sub 非可靠投递（订阅者重启会漏）→ TTL 30min 仍是最终兜底，两机制独立，任一在都正确，只是在时更鲜。

效果：开放期陈旧窗口 ≤ 广播时延（秒级，M9）；命中率因热 TTL 放宽 + 预暖上调目标至 ≥70%（M7）。bypass 规则保留：问句含「现在/实时/重查/刷新」本次直查；boundary 直答（A2）不进缓存。

### 6.4 预暖（消灭每天首问的实时聚合）

- 触发：订阅者收到 `mart:invalidate` 后、以及进程启动时，预计算并写 R1：当日 `channel_sales`（全部+分渠道）、`daily_sales` 分 scope、`sku_inventory` 总览（三态分布+各态 TOP5）；
- 清单来源：初值即上述手置集合；上线后按 R8 问句频次 TOP（tool+参数 digest ZINCRBY）滚动扩充；
- 预计算复用工具执行器纯函数，与查询路径共享 single-flight 锁，不额外打穿生产库。

### 6.5 跨进程协同与入口保护

- **分布式 single-flight**：`SET kbqa:lock:{key} NX PX 30000` 作跨进程层，进程内 per-key 锁仍是第一层；抢锁失败的并发方短等一次后按 miss 直查（fail-open，不排队不阻塞）；
- **msg_id 去重快路径**：`SET kbqa:dedup:{msg_id} NX EX 3600`，命中即钉钉回调重试直接丢弃；DB 唯一键（`kb_qa_audit`）仍是最终兜底；
- **限流**：每发送者 `INCR kbqa:rl:{uid}:{min}` + EX 60，阈值 10 条/分钟（可配），超限回一句限流话术、不进 agent——保护生产库与 LLM 预算。

### 6.6 开关分发（秒级回滚，不重启不登机器）

`kbqa:flags` hash 存 §8 各开关运行时值 + `PUBLISH kbqa:flags`；各进程订阅热更（进程内 dict 叠加在文件 config 之上）。observe→enforce、单层回滚全进程秒级生效；文件 config 仍是 bootstrap 默认值与 Redis 不可达时的兜底真源。

### 6.7 观测与键空间治理（fail-open ≠ fail-silent）

- R7 跨进程汇总 hit/miss/error/token，诊断端点与 badcase 周报读聚合快照（不含键/载荷/DSN，继承既有泄露边界）；
- R11 心跳 + R7 error 计数：**Redis 不可达持续 >5min → 周报 + 日志 ERROR**（M10）；
- 键空间治理：所有键必须带 TTL（实例 maxmemory-policy 部署时探针确认为 `volatile-lru`）；前缀登记表 = 本方案 R1-R11 + 既有四组，新增前缀须登记；每周 SCAN 抽样各前缀键数/内存进周报，实例 used >70% 触发 TTL 与键基数复查；
- 载荷为经营数据：Redis 仅 VPC 内网（DCS2 `192.168.0.6:6379`），TTL 即陈旧暴露上限。

### 6.8 依赖分级与降级矩阵

- 云上进程（kb-gateway / kb-web / dops-scheduler）把 `PUBLIC_DATA_REDIS_URL` 列为**部署必配项**（部署 checklist + 启动探针日志打印 backend 名）；本地 cron 进程无配置自动进程内后端，语义等价现状；
- 代码契约不变：任一角色 Redis 异常 = 该角色独立降级（6.2 表末列），问答主链路永不阻塞在 Redis 上、绝不 503；
- 不新增配置项：复用 `PUBLIC_DATA_REDIS_URL` / `KB_REDIS_URL` 既有环境变量。

### 6.9 与 P2 预聚合的关系

enforce 后若业务问句 p95 仍 >3s 或命中率 <40%，再评估 extract 管线增预聚合表 `agg_sku_daily`（spec_no×日：件数/金额）；有预暖 + 事件失效后预计不触发，达标不建表。

## 10. 风险与取舍

- **过滤/压缩误伤**：observe 期同时覆盖 filter diff 与 focus 压缩 diff；聚焦压缩保留 TOP 3 + others 汇总，总量信息不丢；
- **缓存陈旧**：开放期热 TTL 30min + 事件驱动失效双保险（6.3），陈旧 ≤ 广播时延，pub/sub 漏时 TTL 兜底；答复带 data_version 表述；补录敏感场景用 bypass 词直查；封闭期/快照键带版本，无陈旧面；
- **pub/sub 丢消息/订阅者重启漏失效**：TTL 兜底独立成立，正确性不依赖广播可达性，广播只优化新鲜度；
- **Redis 内存增长**：全键带 TTL + volatile-lru + 每周 SCAN 抽样与 used>70% 水位复查（6.7）；
- **限流误伤**：阈值可配；超限只回一句限流话术、不丢问句语义（1 分钟后重发即正常），observe 期先记不拦；
- **LLM 裁切时延/成本**：仅 >600 字单意图触发，预计 <10% 消息（M6 监控）；
- **SKU 同名多规格**：列 spec_no 清单反问，不猜不合并；
- **缓存键爆炸**：参数规范化 + 期间类别收敛键基数；query_sql 只热层且 sha1 收敛；
- **评测集维护成本**：badcase 周报未命中聚类直接转评测集候选，周更 ≤5 条；
- 不做：向量重排、规则模板通路过滤、audit 扩列、LLM 答案缓存、品牌维度与预聚合表（P2）、多轮 SKU 下钻特殊化（复用现有 history 机制）。
