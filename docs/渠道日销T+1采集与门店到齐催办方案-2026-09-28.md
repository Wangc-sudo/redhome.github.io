# 渠道日销 T+1 采集与门店到齐催办建设方案

**对象**：`http://203.205.91.241:8300/qudao.html`（渠道榜单页，含渠道日销快报等五板块）
**需求**：① 数据采集同步时间改为**次日 10:31**（即每天 10:31 采集并同步**昨天**的数据）；② 若检查到某门店昨天无数据，**@ 该门店负责人**催报。
**状态**：本文件为建设方案，**未改动任何代码**，待评审与口径裁决后进入实施。

---

## 1. 现状盘点

### 1.1 数据链路（渠道日销）

```
钉钉 AI 表（按渠道分 sheet：channel_daily_sales_*）
   └─ sync-dingtalk ──> raw_dingtalk.channel_daily_sales
        └─ extract-mart ──> mart_ops.fact_channel_daily_sales   （店铺粒度）
             └─ pages-qudao ──> /opt/dops/pages-output/qudao.html
```

- 事实表粒度 = **店铺 × 日**：`channel / store_name / business_date / sales_amount / responsible_person(JSON)`，主键 `source_record_id`（AI 表记录 ID），upsert 语义。
- `responsible_person` 落库形态：`[{"name": "张三", "unionId": "..."}]`（见 `common/public_data/extract_ecom_people.py` 的 `parse_owners`）。
- 门店月目标/负责人点名册：`channel_monthly_target` → `fact_channel_store_target`（`store_name / channel / monthly_target / owners_json`，一行一店，全量替换）。

### 1.2 现行调度（`docker/integration/pipelines.seed.yaml`，Nacos 为准）

| service | cron | 说明 |
|---|---|---|
| `sync-dingtalk` | `0 2,7,14,16 * * *` | AI 表**全量**重拉（含渠道日销） |
| `extract-mart` | `0 4,8,15,17 * * *` | raw → mart 投影 |
| `pages-qudao` | `30 8,15,17 * * *` | 生成 qudao.html |
| `channel-daily-qudao` | 停用 | 已并入榜单页 |
| `robot-qudao` | `0 18,20 * * *` | remind/check，但 qudao 区域**无 AI 日报表**（`tableUrl` 为占位），实际不产生渠道门店催办 |

### 1.3 问题

08:30 出页面时，昨日（T-1）各店铺数据往往尚未填齐，页面只能回退显示更早的有效日——2026-09-23 核查已实证：09-22 仅有 4 条预填 0 值行，页面"数据截至 9-21"。**口径没错，但时效性不满足**。且缺失是静默的：没有任何人知道哪几家店没交。

### 1.4 可复用能力

| 能力 | 位置 | 复用方式 |
|---|---|---|
| 定时调度 + Nacos 热更新 + MySQL named lock 防重入 + `depends_on` 门禁 | `common/public_data/scheduler.py` | 新增管线仅需 seed + 命令表登记 |
| 幂等投递（唯一键 `region:kind:business_date[:suffix]`） | `common/public_data/outbox_repository.py` | 重跑不重复发 |
| 群消息 @ 人（`atUserIds`）与 DING | `common/gateway/delivery.py`、`common/dingtalk/client.py` | 新增 kind 即可 |
| 负责人集合解析 / 店铺归属三级回退 | `extract_ecom_people.py`（`parse_owners`、`store_meta_by_store`、`channel_fallback_owners`） | 直接复用，避免归属口径分叉 |
| 渠道日销有效日回退 | `channel_daily.py:resolve_channel_business_date`（日合计非零才算有效，防 0 元假日报） | 保留为兜底 |
| 通讯录（`user_id`/姓名/部门） | `raw_dingtalk.dingtalk_org_member` → `mart_ops.dim_robot_member` | @ 人映射源 |
| 页面按业务日重算 | `mart_cli leaderboard-html --date YYYY-MM-DD` | T-1 重算无需改渲染层 |

### 1.5 缺口（本方案要补的增量）

1. 没有 **T+1 采集窗口**：现有同步都在当日 02/07/14/16，没有"次日早上取昨天"的线。
2. 没有 **门店级到齐校验**：现有 remind/check 是"区域人员 vs 日报事实表"，qudao 区域无日报名单，`dim_robot_member` 无 qudao 成员，无法覆盖门店。
3. 没有 **门店负责人 → 钉钉 userId 映射**：AI 表给的是 `{name, unionId}`，而 `atUserIds` 要 staffId（userId）。
4. 没有 **渠道催办消息通道**：outbox `kind` 未登记（`_KINDS` / `_GROUP_KINDS` / `_ERROR_CODES` 三处需同步新增）。
5. `live-sync` / `extract-mart` 目前**只有 `--source` 过滤，没有 `--dataset` 过滤**，无法只跑渠道日销一条线（需增量参数）。
6. 页面生成时间未与采集对齐。

## 2. 目标与非目标

**目标**
- G1：每天 **10:31** 采集并同步 **T-1（昨天）** 的渠道日销数据，页面以 T-1 为准。
- G2：采集后立即做**门店到齐校验**，缺失门店 **@ 其负责人**（群消息），到齐则静默。
- G3：全过程幂等、可观测、失败不误催。

**非目标**
- 不改渠道日销的**计算口径**（月累计自然日、环比上一工作日、店铺粒度目标链全部沿用）。
- 不引入新的数据存储形态（不新增事实表；点名册优先复用现有表）。
- 不动 ICP/域名/NTP 等基础设施。

## 3. 总体设计

### 3.1 T+1 时序（北京时区）

```
10:31  sync-channel-sales     AI 表渠道日销 → raw         （新增线，仅渠道日销数据集）
  │  depends_on
10:35  extract-channel        raw → fact_channel_daily_sales + fact_channel_store_target
  │  depends_on
10:40  channel-missing-check  门店到齐校验 → robot_outbox（kind=channel_missing，@负责人）
  │  depends_on
10:45  pages-qudao            --date T-1 重算 qudao.html
       （可选）
14:00  channel-missing-recheck 仍缺 → DING 到人（二次催办）
```

- 10:31 为需求指定时间，且天然避开整点（不与 `sync-dingtalk` 02/07/14/16 及 WDT 线争 DB 锁与源 API 配额）。
- 每条线都经 scheduler 的 **named lock + depends_on 门禁**：上游失败则下游不跑，**校验任务在同步失败时必须 fail-closed（跳过催办 + 告警）**，否则会把"管道故障"误报成"门店没填"。

### 3.2 采集范围

建议**只拉渠道日销相关数据集**（`channel_daily_sales*` + `channel_monthly_target`），不复用整条 `sync-dingtalk`：
- 需要给 `live-sync` 增加 `--dataset`（可重复/通配）过滤参数，并给 `extract-mart` 增加同款过滤（或新增 `extract-channel` 管线只投影这两个数据集）。
- 现有 02/07/14/16 的通用同步**保留不动**（其他数据集仍需要），渠道日销被重复同步无害（按 `source_record_id` upsert，幂等）。

### 3.3 T-1 锚定与时区

- `business_date = 今天 - 1 天`，按**北京时区**计算（容器内时间列存 UTC，已有前车之鉴：`extract_channel_ops._business_date_of` 必须 +08:00 换算）。
- 页面顶部"数据截至"固定展示 **T-1** 与采集时刻（如"数据截至 9-27（10:31 采集）"）。
- 保留 `resolve_channel_business_date` 回退：T-1 全渠道皆无有效数据时，回退到最近有效日，并在页面显著标注"⚠️ 昨日数据未到齐，当前显示 X 月 X 日"。

## 4. 门店到齐校验（核心）

### 4.1 应到门店点名册（三选，建议 A+B 并集）

| 方案 | 来源 | 优点 | 缺点 |
|---|---|---|---|
| **A（推荐基线）** | `fact_channel_store_target`（月目标表，一行一店） | 已落库、含负责人与渠道 | 未设月目标的新店/小店可能不在表内 |
| **B（并集补齐）** | 近 30 天 `fact_channel_daily_sales` 的 `store_name` DISTINCT | 自动覆盖新店 | 含已停运店，需排除名单 |
| C（终态） | AI 表新增"在营门店"sheet（含 `is_active`、生效区间） | 最准，可管停运/新开 | 需运维建表与维护 |

- 并集 = 应到门店；再减 **停运/豁免名单**（Nacos `region-qudao.yaml` 新增 `storeExclude: []`，复用现有 overlay 机制，不入 git）。
- P0 先按 A+B 落地，C 作为收敛项。

### 4.2 缺失判定（**待裁决**，见 §6）

| 情形 | 建议判定 | 说明 |
|---|---|---|
| T-1 该店无任何行 | **缺** | 典型未填报 |
| 有行但 `sales_amount IS NULL` | **缺** | 预填空行，等价未填 |
| 有行且 `sales_amount = 0` | **到齐（不催）** | 与"日合计非零才算有效日"的回退口径区分开：门店"填了 0"是已响应，不应催（**请运维确认**） |
| 有行且金额 > 0 | 到齐 | — |
| 店铺名留空（猫超式整渠道留空） | 按**渠道**判，走 `channel_fallback_owners` 归属 | 与现有归属口径一致 |

### 4.3 负责人解析与 @ 映射

owners 来源优先级（与 `build_fact_rows` 完全一致，禁止自造）：
1. 明细行自带 `responsible_person`；
2. 回退该店在 `fact_channel_store_target.owners_json` 的集合；
3. 店铺名为空时走渠道级 `channel_fallback_owners`（仅渠道内集合无歧义时）。

**姓名/uniId → 钉钉 userId（atUserIds 只认 staffId）**：

```
owners_json[{name, unionId}]
  ① unionId  →  raw_dingtalk.dingtalk_org_member.payload_json.unionid → user_id   （首选，需 P0 实测字段存在）
  ② 姓名精确 →  dim_robot_member（跨 region 查；唯一命中即用）
  ③ 同名歧义 →  不 @，转文本点名 + 记 WARNING（沿用 aliases 机制解决）
  ④ 全部落空 →  文本点名 + @ ccUserIds（运营/群主，Nacos 配置）
```

- 映射**只读库、不实时调钉钉 API**（fail-open，通讯录随每日 02:00 组织同步更新）。
- 若 P0 实测 `payload_json` 不含 unionId：备选是请运维在 AI 表负责人旁补一列"钉钉 userId/工号"，或接受"姓名匹配 + 文本兜底"。

### 4.4 消息与幂等

- 新增 outbox `kind = channel_missing`，**三处必须同步登记**：`outbox_repository._KINDS`、`gateway/delivery._GROUP_KINDS`、`_ERROR_CODES`（漏一处会导致入队失败或投递时报 unknown kind）。
- 去重键：`qudao:channel_missing:{T-1}`（**不加时分后缀**）→ 同一天最多一条；二次复核用独立 kind（`ding`）或 `dedupe_suffix`。
- 文案（Markdown，表格）：

```
### 📥 渠道日销数据缺口提醒（9月27日）
以下门店截至 10:31 仍未上报昨日数据，请于今日 12:00 前补填：

| 渠道 | 门店 | 负责人 |
|---|---|---|
| 猫超 | XX旗舰店 | @张三 |

[点此填写](AI 表地址)　（已填报请忽略）
（李四 未匹配到钉钉账号，请手动提醒）
```

- 按**负责人聚合**（一人多店合并一条 @，不按店刷屏）；@ 人数设上限（建议 20），超出部分只列文本 + 抄送运营。
- 全员到齐 → **不发消息**，仅写日志（status=`all_filled`）。

## 8. 风险与对策

| 风险 | 影响 | 对策 |
|---|---|---|
| 同步失败被误判为"门店缺报"，群内乱 @ | 信誉损失、打扰 | 校验任务校验 `sync_run` 成功 + `depends_on` 门禁，失败则跳过催办并告警（fail-closed） |
| unionId 无法映射 userId | @ 不生效 | 三级兜底：unionId → 姓名 → 文本点名 + 抄送；终态由运维在 AI 表补 userId 列 |
| 10:31 之后才填报的店被催 | 误催 | Q4 二次复核可选；文案注明"已填报请忽略"；复核以最新数据为准，不重复 @ 已补齐的人 |
| 月目标表缺新店 → 漏催 | 覆盖不全 | A+B 并集 + 排除名单；终态进 AI 表在营门店 sheet |
| 共管店多人 | 重复 @ | 按负责人聚合去重，整店归集合每人（与现有归属口径一致） |
| Nacos 未同步 | 新调度不生效 | seed 只是兜底，Nacos 为准；发布后按 `tools/nacos_pipelines_check.sh` 复核，改完必须 `publish-pipelines` 或改 Nacos 配置 |
| 群消息打扰 | 业务抱怨 | 单日单条、@ 上限、全员到齐静默 |
