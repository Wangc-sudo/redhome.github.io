# 执行提示词：日报催办止血 + `sync-dingtalk` schema 漂移定位

**背景**（用户反馈，2026-09-29）：「钉钉播报提醒逻辑很乱，有些无需填写数据的人也在提醒他写」。

**配套方案**：`digital-ops/docs/万科大莲花团购群播报改造方案-2026-09-29.md`（根治方案，**本提示词不含 P1 代码改造**，只做止血与定位，A4 裁决要求方案评审通过后才动代码）

**性质**：生产环境**只读体检 + 两处可逆开关 + 一条手动同步**，全程不改业务代码、不改表结构。

**执行方式**：严格按 S1 → S2 → S3 → S4 顺序。S1 没出结论前不要动任何开关。

## 0. 已确认的事实（不必重新论证，直接作为前提）

1. **系统里没有"这个人不用填"的概念**。应填名单 = `dim_robot_member` 中该 region 的**全部在职成员**（`docker/integration/org.seed.json` 区域→顶层部门递归展开，子部门自动纳入），唯一排除条件是 `is_active=1` 与工作日门禁（`dim_calendar`）。**没有免填标记、没有按部门排除、没有应报名册**。

```183:191:digital-ops/common/metrics/daily_report.py
def fetch_region_members(connection, *, region):
    return _fetch_all(
        connection,
        "SELECT `user_id`, `name`, `region`, `dept_id`, `dept_name` "
        f"FROM `{MEMBER_TABLE}` "
        "WHERE `region` = %s AND `is_active` = 1 ORDER BY `name`",
        (region,),
    )
```

2. **vanke 群的催办 100% 失真**（这是"无需填写也被催"的主因）：催办拿**成员姓名**去比对当天 `responsible_person` 集合，而 vanke 写入的是**数据格**（`万科体验馆·零售`），永远匹配不上 → 6 人恒判未填 → 每天 18:00 + 20:00 **@全员 + DING 全员**。吴金澎（体验中心根部门，运维已裁决"不填写任何数据"）照样天天被催。代码位置：`common/daily_robot/mart_tasks.py:109-114` + `common/metrics/daily_report.py:122-135`。

3. **`sync-dingtalk` 已停更 5 天**：近 5 天每日 4 批全部 failed，`failure_code=schema_drift`；raw 层停在 09-24 → `fact_daily_report_offline` 无新行 → hangzhou / shaoxing **同样判全员未填**。这是当前最高优先级生产故障，**也是"渠道填报 09-24 起停止"这条归因需要重估的原因**（可能是填报一直在发生、只是同步挂了进不来）。

4. `broadcastExclude`（如余发兴）**只对榜单生效**（`common/daily_robot/mart_leaderboard.py:120`），`mart_tasks.py` 的 remind/check 完全不读它 → 榜单上不出现的人，群里照样被 @。

## S2. 止血：关掉失真的催办（可逆）

**范围判断（照此执行，不要扩大）**：

- **必须关**：`robot-vanke` —— 催办口径 100% 错，继续跑只会消耗信用（狼来了）。
- **先不关**：`robot-hangzhou` / `robot-shaoxing` —— 失真是同步故障的连带结果，S3 修好后自动恢复；关了会让"真未填"的人失去提醒，且掩盖故障。
- **确认即可**：`robot-qudao` / `robot-junpin` / `robot-offline_all` —— `org.seed.json` 未登记这三个区域的部门，名单应为**空** → 静默。体检时确认其 `dim_robot_member` 计数；若非空需当场记录为异常。

关线（Nacos 为准）：

```
# 云上执行：置 false 并自动回读验证
bash tools/nacos_disable_pipeline.sh robot-vanke.yaml
bash tools/nacos_pipelines_check.sh
```

**三处一致性纪律**：

1. Nacos 改完必须回读确认 `enabled: false`；
2. **同时**把 `docker/integration/pipelines.seed.yaml` 的 `robot-vanke` 改成 `enabled: false` 并注明原因（seed 是 Nacos 抖动时的 fallback，`PipelineConfig.enabled` 默认 True —— **seed 不改，Nacos 一抖动催办就复活**）；
3. **不要**跑 `publish-pipelines` 覆盖全量（会把 Nacos 里其它线的运维手工调整冲掉）。

> 生效时机：scheduler 每 tick 重新解析注册表，**无需重建容器**。改的是配置不是 env，不要 `docker compose up -d`。
> 影响面：只停 18:00/20:00 的提醒与 DING；`pages-vanke` 榜单、报数入口（`@机器人 报数`）、`/未填` 等指令**均不受影响**。

## S3. 定位 schema 漂移（最高优先级，阻塞一切）

手动跑一次 dingtalk 源同步，拿**完整报错**（不是调度日志里的收敛码）：

```
docker exec -w /opt/dops/repo dops-scheduler python3 -m common.public_data.cli live-sync \
  --live-read --confirm-local-test-write \
  --source dingtalk \
  --source-credentials /opt/dops/live/source-credentials.json \
  --service sync-dingtalk
```

- 若输出 `status=skipped reason=disabled`：说明 `_pipeline_enabled` gate 命中，改用 `--service <容器 $PUBLIC_DATA_SERVICE_ID>`，或先确认 Nacos `sync-dingtalk.yaml` 的 `enabled`。
- 报错中定位 **具体哪张 AI 表 / 哪一行哪一列** 与 manifest 声明不符（`DingTalkReadError`）。

**裁决点（不要自作主张二选一）**：

- 表结构被人为改动 → 回退表结构；
- manifest 声明过时 → 修 manifest。

修完重跑上面那条命令，确认 `status=completed`，再跑一次 `extract-mart` 重建 mart：

```
docker exec -w /opt/dops/repo dops-scheduler python3 -m common.public_data.cli extract-mart --confirm-local-test-write
```

## 2. 已知坑（照做，别踩）

- **Nacos 为准**：改 `pipelines.seed.yaml` 不发布就不生效；反之 Nacos 抖动会回退 seed 且默认 enabled=True → 两边都要改（S2 纪律）。
- **只读纪律**：S1 全程只读，禁止 DELETE/UPDATE；`王城` 测试残留、`9a04049d` 卡 started 的 run 都**留待裁决**，本次不动。
- **时间列存 UTC**（`sync_runs`、`robot_outbox`、raw `synced_at`），换算北京 +8。
- **DictCursor**：`db.connect` 是 DictCursor，**不要 `dict(fetchall())`**（会把单行两列捏成 `{'status':'COUNT(*)'}` 假行），按键取值。
- **Windows/PowerShell**：多行 `python -c` 必炸 → 一律本地写文件再注入；`curl` 是 `Invoke-WebRequest` 别名，用 `curl.exe`；`>` 重定向会毁二进制流 → 远端落盘再取。
- **容器**：`docker cp` 对只读挂载失效 → 用 `cat file | docker exec -i ... ` 管道注入；改 env_file 必须 `compose up -d`，`restart` 不生效（本次不涉及）。
- **不要顺手改代码**：本次零代码改动，任何"顺手把格口径修了"的冲动都停下——P1 需先评审。
