### 1.1 `fact_daily_report_offline`：索引与查询形态错位（P0）

bi-web 最高频的查询形态是**只按 `business_date` 过滤**（`queries.py:45-57`、`501-528`、`580-601`：月累计/年累计/按日分组/MAX(business_date)）：

```sql
SELECT COALESCE(SUM(sales_amount), 0)
FROM fact_daily_report_offline
WHERE business_date >= DATE_FORMAT(CURDATE(), '%Y-%m-01')
```

现有两个复合索引的最左列分别是 `region` 和 `responsible_person`，**按最左前缀原则都无法命中**，全部退化为全表扫描。同样受影响的还有 `GROUP BY department`（`queries.py:540-547`，无任何索引可用，临时表 + filesort）。

**建议**：新增迁移版本（不改旧版本文本，遵守校验和红线），加单列索引：

```sql
ALTER TABLE `fact_daily_report_offline`
  ADD KEY `idx_business_date` (`business_date`);
```

> ✅ 2026-09-17 已落地：迁移版本 `mart-extract-daily-report-date-index-v1`（mart 侧）；`mart-facts-v1` 因尚未在任何库应用，直接追加同一条 ALTER 保持新 schema 结构完整。

（`fact_channel_daily_sales` 已有 `(business_date, store_name)` 可命中同形态查询，无需补。）

### 1.2 `fact_order_line`：当前够用，是第一个需要容量规划的表

bi-web 形态为 `WHERE trade_time range + GROUP BY spec_no/brand/channel`（`queries.py:115-120`、`172-185`、`389-392`）：`idx_order_line_time` 能圈定范围，GROUP BY 走临时表。行数万级内无感；**触发条件：单表 > 20 万行或月榜查询 > 500ms 时**，加覆盖索引 `(trade_time, spec_no, paid_amount)` 消除回表。

### 1.3 raw 层与控制面：索引覆盖良好

`read_dataset` 已支持 `synced_at` 水位增量（`extract_mart.py:170-192`，原架构债 #3 已修），`idx_synced_at` / `idx_source_window` 均在；`read_org_members` 的相关子查询（`extract_mart.py:245-253`）表小无压力。

## 2. 写路径写放大

### 2.1 `upsert_fact` 逐行 round-trip（P1，架构债 #4）

```194:215:common/public_data/extract_mart.py
        with contextlib.closing(self._mart.cursor()) as cursor:
            for row in rows:
                params = [row.get("source_record_id")]
                params += [row.get(name) for name in dataset.target_columns]
                params += [synced_at, sync_run_id]
                cursor.execute(sql, tuple(params))
```

每行一次网络 round-trip。2804 行无感，10 万行就是 10 万次往返。**建议**：改 `cursor.executemany(sql, all_params)`（仓内 `replace_table` 已是 executemany，有现成范式），行为等价、纯性能改动。

> ✅ 2026-09-17 已落地：`upsert_fact` 改为单次 `executemany`，空行集短路不触库。

### 2.2 7 个数据集仍整表 DELETE+INSERT（P2，架构债 #12）

`replace_table`（`extract_mart.py:140-168`）覆盖 5 × `fact_fin_*` + `dim_product` 镜像 + `fact_order_line`：每轮 extract 整表删除重写。前置未解（目标表无稳定行级键、源侧无水位），**维持现状**；触发条件：单表 > 10 万行或 extract 窗口明显拉长。届时优先做 `fact_order_line`（增长最快），方案是「`(trade_no, line_no)` 已有稳定键 + raw 侧 `synced_at` 水位」的 upsert+剪枝。

### 2.3 `read_mart_mirror` 全表读入内存（P2）

`extract_mart.py:136-138` `SELECT * FROM dim_product` 每轮全量载入做品牌反查。商品表千级无感；万级以上应改为「只 SELECT 反查所需列（`spec_no`, `brand_name`）」并考虑投影侧 JOIN 下推。

> ✅ 2026-09-17 已落地：`read_mart_table` 增加 `columns` 投影参数（带标识符校验），`_brand_index` 只读 `spec_no`/`brand_name` 两列。

## 6. DB 建表门禁（2026-09-17 上线）

新增 `tests/common/test_db_ddl_gate.py`，随单测套件强制运行，三道闸：

1. **DDL 集中登记**：扫描 `common/`、`数字化/` 全部生产代码，`CREATE/ALTER/DROP TABLE` 只允许出现在白名单模块（`live_migrations.py`、各 schema 定义模块、两个有书面理由的独立脚本）。任何业务代码私自建表 → 测试红，并提示登记进 `_MIGRATIONS` 的正确姿势；
2. **迁移注册纪律**：版本号命名规范（`xxx-v\d+`）、target 必须属于已知 schema 集合（含拆库三个新 target）、`CREATE TABLE` 必须 `IF NOT EXISTS`（可重放）、迁移内禁止 `DROP TABLE`（破坏性变更走人工评审的运维脚本）；
3. **新表必须有主键**：登记进迁移的每张表必须声明 `PRIMARY KEY`，且同一 target 内不得重复建同名表。
