# DB 大表治理手册（通用方法论）

日期：2026-09-17 · 定位：方法论参考，与《db-大表排查报告-2026-09-17》（本项目落地清单）配套

---

## 0. 第一性原理

大表问题的本质是**单表数据量超过了「访问路径可以有效裁剪」的临界点**。治理手段按成本从低到高排成一个阶梯，**永远先爬低级台阶，跳级是过度设计**：

```
索引/查询改写 → 分区 → 归档 → 读写分离/缓存 → 分库分表
   小时级        天级     天级      周级          月级+永久复杂度
```

判断标准不是行数本身，而是**行数 × 访问形态**：1 亿行只按主键点查的表无需治理，100 万行全表扫的报表表已经是问题。

---

## 1. 台阶一：索引与查询治理（90% 的「大表问题」止步于此）

**索引侧：**
- 对账访问路径与索引：慢查询的 WHERE/JOIN/ORDER BY 列 ↔ 索引最左前缀。复合索引按「等值列在前、范围列在后、高基数在前」排序；
- 覆盖索引消除回表：把 SELECT 列全部包进索引（如报表查询 `(trade_time, spec_no, paid_amount)`）；
- 警惕索引过多：每个索引都是写放大，定期用 `sys.schema_unused_indexes` 清理。

**查询侧：**
- 深分页 `LIMIT 100000, 20` → 游标分页 `WHERE id > ? ORDER BY id LIMIT 20`；
- `SELECT *` → 列裁剪；
- 函数包裹索引列（`DATE(trade_time) = ?`）→ 改写为范围条件让索引生效；
- 大 IN 列表 / 大 JOIN → 分批或临时表；
- `COUNT(*)` 大表精确计数 → 近似值 / 汇总表。

**工具**：`EXPLAIN`（重点看 `type` 列：ALL=全表扫描是红线）、slow log、`performance_schema`。

---

## 2. 台阶二：分区（Partitioning）

单表超千万、且有**清晰的时间/范围访问局部性**时考虑。

- **价值**：分区裁剪（查询只扫相关分区）、按分区快速 DROP 归档（秒级 vs DELETE 几小时）、分散索引体积；
- **代价与坑**：MySQL 分区表**主键/唯一键必须包含分区键**（常常倒逼改主键）；跨分区查询反而更慢；分区数有上限（8192，实用中保持 < 200）；
- **典型形态**：`PARTITION BY RANGE COLUMNS(business_date)` 按月/按年 + 滚动加分区、历史分区转只读或 DROP。

**误区**：分区不提升点查性能，也不能替代索引——它是「批量裁剪与生命周期管理」工具。

---

## 3. 台阶三：归档与冷热分离

- **冷数据归档**：超期的历史数据搬到归档库/归档表（如 `fact_order_line_2024`）或廉价存储（OSS + 外表）。业务查询默认只碰热表，需要历史时显式查归档；
- **汇总代替明细**：报表高频访问的口径物化成日/月汇总表（summary/mart），明细只供下钻——这是数仓分层（ODS→DWD→DWS→ADS）的核心动机；
- **生命周期制度**：每张表建表时就定好 TTL 与归档策略，比事后补救便宜一个数量级。

---

## 4. 台阶四：读写分离与缓存

- **读写分离**：读流量打到只读副本。注意主从延迟对「写完即读」场景的影响（强制走主或读己之写）；
- **缓存**：热点读放 Redis。明确 cache-aside 失效策略与穿透/击穿/雪崩防护；缓存必须有命中率指标，否则无法评估价值（本项目 bi-web 已有 `CacheMetrics` + `/diagnostics/cache`，是正确范式）；
- **物化视图/预聚合**：定时任务把重口径算好落表，查询变 O(1)。

---

## 5. 台阶五：分库分表（最后的手段）

单实例写瓶颈或单表超亿级、上述手段用尽后才考虑。

| 形态 | 适用 | 代价 |
|---|---|---|
| **垂直拆分**（按业务域分库，如本项目 mart_facts/mart_dims/mart_queue） | 职责边界、权限粒度、备份粒度 | 低：同实例 schema 拆分即可获得大部分收益；跨库 JOIN 需应用层处理 |
| **水平分片**（sharding，按 sharding key 取模/范围） | 单表亿级、写 QPS 瓶颈 | 高：分布式 ID、跨片 JOIN/排序/事务、扩容再均衡、路由中间件，**永久复杂度** |

**决策红线：**
1. 能用垂直拆分解决就不上水平分片；
2. sharding key 选择即命运：必须覆盖最高频查询的过滤条件（否则全片广播），且分布均匀防热点；
3. 跨实例拆分前必须消灭跨库单条 SQL JOIN（本项目 `fetch_unfilled_members` 就是锁死拆分粒度的先例）；
4. 灰度迁移的标准动作：**双写 → 校验（行数/主键集合/digest/金额 SUM）→ 切读 → 稳定观察 → 停旧写 → 旧表退役**，每步有独立回滚路径（详见《mart 拆库设计》§2.5-§3）。

---

## 6. 替代与兜底技术选型

| 场景 | 考虑 |
|---|---|
| 分析型大查询拖垮 TP 库 | 数据同步到列存 OLAP（ClickHouse / Doris / MaxCompute），TP/AP 分离 |
| 写入吞吐瓶颈（日志/事件流） | MQ 削峰 + 批量落库；触发条件参考「日写入 > 1 万行 或 consumer > 2」以下的轮询方案通常是负资产 |
| 弹性与免运维 | 云原生数据库（PolarDB/TiDB 等）的水平扩容，本质是「把分片复杂度外包给数据库」 |
| 备份恢复粒度 | 大表按库/schema 隔离备份策略，核心表与非核心表分开保留周期 |

## 7. 治理流程（制度比技术重要）

1. **基线**：slow log 常开 + 每月 `information_schema` 体量体检，增速前 3 的表进观察名单；
2. **预算**：每张核心表建档——当前行数、月增速、预期 1 年体量、访问形态、TTL；
3. **触发条件写死**：每个优化项都要有量化的「何时动手」（如「表 > 20 万行或查询 > 500ms」），避免拍脑袋提前优化，也避免拖成事故；
4. **变更纪律**：DDL 版本化、校验和防漂移、ALTER 优先 `ALGORITHM=INPLACE, LOCK=NONE`，大表 DDL 用 gh-ost/pt-osc 在线变更；
5. **回滚预案**：任何迁移落地前先写回滚路径，旧表退役必须滞后于「切读稳定 ≥ 2 周 + 一轮完整对账」。
