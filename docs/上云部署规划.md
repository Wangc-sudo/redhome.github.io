# digital-ops 上云部署规划

> 规划时间：2026-09-16
> 目标资源：ECS 2C4G/40G ×2、ECS 4C8G/40G ×1、RDS MySQL **8.0** 主备 ×1、Redis 7.0 2GB ×1
> 网络前提：**全部资源同一可用区、内网互通**（已确认）
> 依据：全仓 SQL 兼容性扫描结果 + `live_safety.py` / `db.py` / `docker-compose.integration.yml` 实读

## 一、两个先说结论的判断

### ✅ 判断 1：MySQL 8.0 完全可用，而且**比 8.4 更好**

全仓扫描结论：**零 MySQL 8.4 专属依赖**。

| 证据 | 位置 |
|---|---|
| 代码自述下限就是 8.0 | `outbox_repository.py:92` 「目标库为 **MySQL 8.0+**（集成环境 8.4）」 |
| 唯一版本门槛是 8.0.1 就有的 `SKIP LOCKED` | `outbox_repository.py:104`（且留了 `skip_locked=False` 退化开关） |
| 全仓无 CTE、无窗口函数、无 `JSON_TABLE`、无 `GROUP_CONCAT`、无 Hint | 扫底为「MySQL 5.7 语义子集 + SKIP LOCKED」 |
| `ONLY_FULL_GROUP_BY` 全部合规 | 逐条核对 `queries.py` 的 8 处 GROUP BY |
| DDL 只用 InnoDB + `utf8mb4_0900_ai_ci` | 后者是 MySQL 8.0 的默认排序规则 |
| 认证无插件写死 | `db.py:11-20` 不指定 auth plugin；`PyMySQL 1.1.1 + cryptography 50.0.1` 覆盖 `caching_sha2_password` |

**额外收获**：RDS 从 8.4 换成 **8.0 后，Nacos 的兼容性风险自动消失**。
之前登记的风险是「Nacos 2.4.3 官方只支持 MySQL 5.7/8.0，我们是 8.4，驱动未验证」——现在 8.0 落在官方支持矩阵内，**Nacos 可以直接接 RDS 做持久化**（见 §4.3）。

### 🔴 判断 2：生产路径被**两道闸门互相锁死**，必须先改

不止 `live_safety.py` 一处。扫描时发现了第二道闸门，两者叠加形成**死锁**：

**第二道闸门** `common/public_data/settings.py:93-98`：

```python
for database_name in database_names.values():
    is_test_database = database_name.endswith("_test")
    if app_env == "test" and not is_test_database:
        raise ValueError("APP_ENV=test requires database names ending in '_test'")
    if app_env == "production" and is_test_database:
        raise ValueError("APP_ENV=production rejects database names ending in '_test'")
```

**死锁矩阵**——四种组合只有一种能走通：

| APP_ENV | 库名 | `settings.py` | `live_safety.py` | 结果 |
|---|---|---|---|---|
| `test` | `*_test` | ✅ | ✅ | ✅ **唯一可行**（本地 dispose 容器） |
| `production` | 正式名 | ✅ | ❌ app_env 必须 test | ❌ |
| `production` | `*_test` | ❌ production 拒绝 _test | — | ❌ |
| `test` | 正式名 | ❌ test 要求 _test | — | ❌ |

> **结论：`APP_ENV=production` 这条分支在代码里从未真正走通。**
> README 写着"必须显式设置 `APP_ENV` 为 `test` 或 `production`"，
> 但 production 只是被 `settings.py` 承认的取值，随即被 `live_safety.py` 否决。
> 换句话说：**代码目前只实现了"本地集成测试"这一种运行模式。**

下面是第一道闸门的细节：

`common/public_data/live_safety.py` 是一道**五重安全门禁**，四条会挡住上云：

```python
def _require_local_test_target(settings, values):
    if settings.app_env != "test":                       # ① APP_ENV 必须 test
        raise LiveRunRejected("APP_ENV must be test")
    if values.get("INTEGRATION_TEST_RUNNER") != "1":     # ② 必须是集成测试容器
        raise LiveRunRejected("INTEGRATION_TEST_RUNNER must be 1")
    if any(database.host != "mysql" for database in databases):   # ③ host 必须是 compose 服务名
        raise LiveRunRejected("PUBLIC_DATA_RDS_HOST must be mysql")
    names = tuple(database.name for database in databases)
    if names != ("raw_dingtalk_test", "raw_wdt_test", "mart_ops_test"):  # ④ 库名必须带 _test
        raise LiveRunRejected(...)
```

这四条被 `require_live_run` / `require_extract_run` / `require_business_run` / `require_gateway_run`
（`:32 :41 :54 :67`）共用 —— **sync-dingtalk、sync-wdt、extract-mart、robot、pages、dingtalk-gateway 全线被拒**。

> 这不是 bug，是有意的写保护（防止误连生产库）。上云要做的**不是删掉它**，
> 而是把"必须指向本地 dispose 容器"改成"必须指向受控的云目标"，同时保住防误连能力。改造方案见 §5.1。

### 同可用区带来的三个改善

| 原来的风险 | 现在 |
|---|---|
| 🔴 ECS 与 Redis 不同 VSwitch → 25s 超时连不上（已实测） | ✅ 同区同段，三台 ECS 均可连 Redis |
| 🟡 Nacos 跨可用区 → `bi_web/config.py` 每 30s 缓存刷新撞 4s 超时惩罚 | ✅ 同区 RTT 亚毫秒，惩罚窗口基本不会触发 |
| 🟡 跨 AZ 访问 RDS 主库，主备切换期间抖动 | ✅ 同区直连，切换影响最小 |

### 为什么这样分

**ECS-App 用 4C8G（而不是随便挑一台）**

| 理由 | 说明 |
|---|---|
| 两个长驻服务 | bi-web + dingtalk-gateway 常驻，gateway 还挂着 Stream 长连接 |
| cron 并发 | `pipelines.seed.yaml` 里 sync-dingtalk 与 sync-wdt **同为 `0 2 * * *`**，会同时跑 |
| 内存余量 | `robot`/`pages` 是 Python 一次性容器，峰值叠加需要余量 |
| 时区敏感 | `CURDATE()` 驱动月份窗口，同机保证 Python 与 SQL 同月 |

**ECS-Ctrl 用 2C4G 跑 Nacos**

- Nacos JVM `XMX=1g`（同区后可调高）+ 堆外，实际常驻 1G 上下，2C4G 够用
- **控制面独占一台**：业务容器重启 / 发版 / OOM 都不会波及配置中心
- Nacos 是唯一掌握真实 robotCode 的组件，独立部署也缩小了暴露面

**ECS-CI 用 2C4G 跑交付面（这台的定位很关键）**

把**构建与测试从生产机剥离**：

- `frontend/` 有 7500+ 文件，本地构建 Docker 镜像相当吃内存，不该在跑业务的机器上做
- 448 例集成测试（含 `test-runner` 需要启 MySQL）应在独立环境跑
- **同区后灾备价值大幅提升**：与 ECS-App 同区同网，共享同一套 RDS/Redis/Nacos，
  镜像同步到位即可直接拉起顶替，无需改任何连接配置

> 这解决了原方案里"ECS-A 只有 2C4G 还要兼顾构建"的困境。

## 三、前置校验（动手之前先跑一遍）

### 3.1 Redis 白名单——同区≠自动放行，仍要显式配置

> ⚠️ 同可用区**不等于**白名单放行。白名单是实例级访问控制，与可用区无关。
> 实测参照：既有环境里 Redis 位于 `172.23.6.98`，同 VSwitch 的 ECS 秒连，
> 而跨段的 ECS 25s 超时 —— 原因是白名单，不是路由。

**做法**：控制台 → Redis 实例 `r-bp1dg4ctmqh8c0fqv3` → 白名单设置，
把三台 ECS 的私网 IP 全部加入（或直接放 VPC 网段）。

**验收**（三台都要跑，都要过）：

```bash
python3 -c "import socket;s=socket.create_connection(('r-bp1dg4ctmqh8c0fqv3.redis.rds.aliyuncs.com',6379),20);s.sendall(b'PING\r\n');print(s.recv(32))"
```

期望 `b'+PONG\r\n'`。同区后如果还有一台不通，一定是白名单，不是网络。

> 提醒：连接超时别按默认 5s/10s 配，实测首次建连可能超 10s，建议 ≥20s。

### 3.2 RDS 参数（两个必须确认）

```sql
SHOW VARIABLES LIKE 'time_zone';                  -- 必须 Asia/Shanghai
SHOW VARIABLES LIKE 'innodb_default_row_format';  -- 必须 Dynamic
SHOW VARIABLES LIKE 'default_collation_for_utf8mb4';  -- 应为 utf8mb4_0900_ai_ci
```

> **`time_zone` 这条是硬要求**：原先靠 compose 里 mysql 容器的 `TZ: Asia/Shanghai` 实现
> （`docker-compose.integration.yml:19-21` 有明确注释）。去掉本地容器后，
> `queries.py:46 :504` 等的 `DATE_FORMAT(CURDATE(), '%Y-%m-01')` 月窗口会错位。

## 五、两个需要决策的点

### 5.1 安全门禁怎么改

#### 先理解它的设计意图（这决定了改法）

这套门禁来自 `docs/superpowers/specs/2026-09-10-restricted-live-public-data-sync-design.md:34-41`，
原文列出了"受限实时同步"启动命令必须同时具备的条件：

```
- APP_ENV=test；
- INTEGRATION_TEST_RUNNER=1；
- PUBLIC_DATA_RDS_HOST=mysql；
- raw_dingtalk_test、raw_wdt_test、mart_ops_test；
- CLI 的 --live-read 与 --confirm-local-test-write 两个独立确认参数；
- 从仓库外部只读挂载的来源 manifest 与钉钉、WDT 凭据文件。
```

**意图**：让开发者能用**真实数据源**联调，但**写入只能落在一次性 dispose 库**，
绝不污染任何持久库。这是个好设计——`测试环境配置单.md:95` 也写着
「写库命令均有 `--confirm-local-test-write` 安全门，误连生产库会被拒绝」。

**问题**：判据被硬编码成了"本地 compose 环境"的字面量。
意图（只写受控目标）依然成立，但判据（`host == "mysql"`、`app_env == "test"`）已经不适用于云上目标。

> 所以准确说法**不是"放行"，而是"把判据从字面量换成契约"**——
> 锁换锁芯，不是拆锁。

#### 要改两处（两道闸门都得动）

| 文件 | 现状 | 改法 |
|---|---|---|
| `live_safety.py:14-29` | 硬编码 `app_env=="test"` / `host=="mysql"` / 三个 `_test` 库名 | 合法目标改为按 profile 解析 |
| `settings.py:93-98` | `production` 与 `_test` 互斥 | 与上一处使用**同一套 profile 规则**，避免两边再次打架 |

> ⚠️ 两处必须**一起改**。只改 `live_safety.py` 会撞上 `settings.py` 的 `_test` 互斥规则，
> 只改 `settings.py` 会被 `live_safety.py` 的 `app_env=="test"` 拦下——这正是当前的死锁形态。

#### 方案对比

| 方案 | 做法 | 评价 |
|---|---|---|
| A 保留 `_test` 库名 + host 白名单 | 云上库仍叫 `raw_dingtalk_test`…，`APP_ENV` 维持 `test`，仅放宽 host 判定 | 改动最小，但**生产库叫 `_test` 极易误导**；且 `APP_ENV=test` 会让"测试环境"语义失真 |
| **B 引入 target profile** | 新增变量（如 `PUBLIC_DATA_TARGET=local-dispose \| cloud-managed`），两道闸门按 profile 取各自的合法 host + 库名集合 | **推荐**。显式、可评审、可单测；`local-dispose` 完全保留现有行为，回归零风险 |
| C 直接删门禁 | — | ❌ 不推荐，等于放弃"误连生产库"的最后一道闸 |

#### 推荐方案 B 的具体形态

```python
# live_safety.py（示意）
_TARGETS = {
    "local-dispose": {          # 现状，一字不改
        "app_env": "test",
        "host": "mysql",
        "names": ("raw_dingtalk_test", "raw_wdt_test", "mart_ops_test"),
    },
    "cloud-managed": {          # 新增
        "app_env": "production",
        "host": os.environ["PUBLIC_DATA_RDS_HOST"],   # 由部署侧注入，不走字面量
        "names": ("raw_dingtalk", "raw_wdt", "mart_ops"),
    },
}
```

配套要求：

- `settings.py` 的 `_test` 互斥规则改为**查同一张表**，而不是自己另写一套 `endswith("_test")` 判断
- 保留 `--confirm-local-test-write` 旗标（可考虑改名 `--confirm-write-target`，但那是另一件事）
- 补单测：`local-dispose` 全部现有断言保持绿；新增 `cloud-managed` 的放行/拒绝用例
- `tests/test_integration_environment.py` 的 compose 合约测试不受影响（它断言的是 compose 形态）

**注意**：方案 A 与 B 的取舍直接影响 §4.4 的库名——选 B 就用正式库名（`raw_dingtalk` / `raw_wdt` / `mart_ops`），
选 A 则沿用 `_test` 后缀。这个决策要在建库之前定下来，否则要重建。

### 5.2 高可用预期要说清

这套配置里：

| 组件 | 是否高可用 |
|---|---|
| RDS MySQL 8.0 | ✅ 主备，自动切换 |
| Redis 2GB 标准版 | ❌ 单点（但 fail-open，挂了不致命） |
| ECS-App（bi-web + gateway） | ❌ 单点，ECS-CI 只做冷备 |
| Nacos | ❌ 单点（standalone） |

**ECS 与 Nacos 是单点**，需接受"单机故障 → 看板不可用 + 机器人停发"。
若要高可用，下一步是 ECS-App 双机 + SLB、Nacos 集群（3 节点）。当前配置不足以做。

### 新增：全部同可用区 = 可用区级单点

统一到一个可用区换来了网络简单，代价是**失去了可用区级容灾**：

| 故障面 | 影响 |
|---|---|
| 单台 ECS 宕机 | 该角色服务中断（App 挂 → 看板 + 机器人停） |
| **可用区整体故障** | **RDS 主备同时不可达 + 三台 ECS 全挂 → 全站不可用** |

RDS 主备只解决实例级故障，**不跨可用区则无法抵御 AZ 级故障**。

**当前建议接受这个取舍**，理由是：

1. 本系统是内部运营工具（日报 + 看板），短时中断可接受，不是交易链路
2. 拿 AZ 级容灾要付出的成本（跨 AZ 部署 + 主备切换 + Redis 跨 AZ 白名单）远高于收益
3. 同区换来的是实测可验证的简单网络，降低日常运维出错概率

**但必须把下面三件事做扎实**，把单点故障的恢复时间压到最短：

- [ ] **ECS-App 的系统盘做快照策略**（每日自动快照），整机可重建
- [ ] **凭据与种子文件异地留存**：`source-credentials.json`、`regions-prod.json`、
      `pipelines.seed.yaml`、`bi.seed.yaml` 的发布副本存到仓库外且有多份，
      否则 Nacos 那台挂了又没备份，真实 robotCode 就丢了
- [ ] **演练一次 ECS-CI 顶替 ECS-App**，确认分钟级可切（同区同网，这个演练成本很低）

> 若日后业务要求提高，再评估跨可用区双活；届时要一并重做 Redis 白名单与 Nacos 部署位置。
