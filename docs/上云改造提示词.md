# digital-ops 上云改造提示词

> 用途：把这份提示词整体交给 AI 执行。分两个阶段——先敲定架构，再做代码适配。
> 特点：自足。包含全部已确认事实与已知陷阱，无需重新探索即可开工。
> 目标环境：Linux（Ubuntu 24.04 LTS），全部资源同一可用区、内网互通。

---

## 提示词正文（以下整体复制给 AI）

---

你是 digital-ops 项目的云迁移工程师。这个项目是一套钉钉运营机器人 + BI 看板系统，现在要从「本地 Windows + Docker Compose 集成环境」迁移到「阿里云 ECS 生产环境」。

请分两个阶段工作：**阶段一敲定架构并出具方案，等我确认后再进入阶段二做代码适配。** 不要跳过阶段一直接改代码。

### 一、项目现状（已确认事实，不要推翻，直接采用）

**技术栈**：Python 3.12 + FastAPI(uvicorn) + PyMySQL + docker compose 编排。
仓库根目录有 `docker-compose.integration.yml`，定义了 12 个服务，靠 compose profile 切分调度。

**服务清单与形态**：

| 服务 | profile | 形态 | 说明 |
|---|---|---|---|
| `mysql` | 默认 | 长驻 | 本地 mysql:8.4 容器，**上云后要移除** |
| `nacos` | `nacos` | 长驻 | 配置中心/注册中心，v2.4.3 |
| `sync-dingtalk` / `sync-wdt` | `live-sync-*` | 一次性 cron | 从钉钉/旺店通拉数据写 raw 库，持凭据 |
| `extract-mart` | `extract` | 一次性 cron | raw → mart_ops 投影，零凭据 |
| `project-mart` | `project` | 一次性 | 单线重建投影 |
| `robot-hangzhou` / `robot-vanke` | `robot` | 一次性 cron | 生成日报写入 robot_outbox |
| `pages-hangzhou` / `pages-vanke` | `pages` | 一次性 cron | 生成榜单 HTML |
| `dingtalk-gateway` | `dingtalk-gateway` | **长驻** | 轮询 outbox 投递钉钉，持凭据，Stream 长连接 |
| `bi-web` | `bi-web` | **长驻** | FastAPI 看板后端，只读 mart_ops |
| `redis` | `bi-web-redis` | 长驻可选 | 卡片缓存，**fail-open** |

**目标云资源（已确定）**：

- ECS：2C4G/40G ×2 + 4C8G/40G ×1，Ubuntu 24.04 LTS
- RDS：MySQL **8.0** 主备 ×1（注意不是 8.4）
- Redis：7.0 标准版 2GB ×1
- 网络：全部同一可用区，内网互通
- 三个业务库必须在**同一个 RDS 实例**（`settings.py:109-114` 共用一份 host/port/user/password，无法拆分）

**已完成的前置结论（直接采用，不用重新验证）**：

1. **MySQL 8.0 完全兼容**。已做全仓 SQL 扫描：0 处 8.4 专属特性，无 CTE / 窗口函数 / JSON 下推 / 优化器 Hint，`ONLY_FULL_GROUP_BY` 全部合规，唯一版本门槛是 `FOR UPDATE SKIP LOCKED`（MySQL 8.0.1+，代码注释自述"目标库为 MySQL 8.0+"）。
2. **Nacos 是必需组件，不是可选件**。种子文件 `docker/integration/regions.seed.json` 里 robotCode / openConversationId 是 `<占位符>`，且有单测 `test_shipped_seed_keeps_placeholders_out_of_git` 守着。真实值只走 Nacos（`阶段4切换运行手册.md` §1）。不发 Nacos 机器人就是坏的。代码层的 fail-open 只是容错，不是"可以不部署"。
3. **Redis 需要显式配置白名单**。同可用区不等于自动放行——实测过同 VPC 不同 VSwitch 的机器 25s 超时，而同段机器秒连，差别在白名单不在路由。
4. **Redis 首次建连可能超过 10s**。连接超时必须 ≥20s，否则出现"能连却报超时"的假故障。

### 二、已知的两个硬阻塞（必须解决，这是改造的核心）

#### 阻塞 1：生产路径被两道闸门死锁

`APP_ENV=production` 在代码里**从未走通过**。两道闸门互相矛盾：

**闸门 A** `common/public_data/live_safety.py:14-29`：

```python
if settings.app_env != "test":                       # ① 必须 test
    raise LiveRunRejected("APP_ENV must be test")
if values.get("INTEGRATION_TEST_RUNNER") != "1":     # ② 必须是集成测试容器
    raise LiveRunRejected("INTEGRATION_TEST_RUNNER must be 1")
if any(database.host != "mysql" for database in databases):   # ③ host 必须是 compose 服务名
    raise LiveRunRejected("PUBLIC_DATA_RDS_HOST must be mysql")
names = tuple(database.name for database in databases)
if names != ("raw_dingtalk_test", "raw_wdt_test", "mart_ops_test"):  # ④ 库名必须带 _test
    raise LiveRunRejected(...)
```

**闸门 B** `common/public_data/settings.py:93-98`：

```python
if app_env == "test" and not is_test_database:
    raise ValueError("APP_ENV=test requires database names ending in '_test'")
if app_env == "production" and is_test_database:
    raise ValueError("APP_ENV=production rejects database names ending in '_test'")
```

**死锁矩阵**（只有第一行走得通）：

| APP_ENV | 库名 | settings.py | live_safety.py | 结果 |
|---|---|---|---|---|
| test | `*_test` | ✅ | ✅ | ✅ 唯一可行 |
| production | 正式名 | ✅ | ❌ | ❌ |
| production | `*_test` | ❌ | — | ❌ |
| test | 正式名 | ❌ | — | ❌ |

这四条检查被 `require_live_run` / `require_extract_run` / `require_business_run` / `require_gateway_run`
（`live_safety.py:32 :41 :54 :67`）共用，**sync / extract / robot / gateway 全线受影响**。

**设计意图（必须保留）**：来自 `docs/superpowers/specs/2026-09-10-restricted-live-public-data-sync-design.md:34-41`，
目的是"能用真实数据源联调，但写入只能落在受控目标，绝不污染持久库"。
**要改的是判据（硬编码字面量），不是删掉意图。**

#### 阻塞 2：compose 默认指向本地 mysql 容器

`docker-compose.integration.yml` 里所有服务的 `PUBLIC_DATA_RDS_HOST: mysql`、`depends_on: mysql`。
上云后要移除 mysql 服务，改指向 RDS。

### 三、阶段一：架构敲定（先做这个，输出方案等我确认）
