# 填报权限与渠道指标统一管理方案（2026-10-07）

> 起源（运维裁决）：「填报名册（谁可以填哪些店/区域）与指标走程序录入应该有关联」。
> 本方案把两条已建成但平行的线——**填报名册**（权限）与**月目标程序导入**（指标）——
> 合并为一套以「填报单元」为中心的管理模型，换月滚动一次到位、全程去黑屏。

## 1. 背景：为什么要关联

| 痛点 | 现状 |
|---|---|
| 负责人两处维护 | 目标 JSON 的 `owners`（指标线）与名册 `person_name`（权限线）各写一份，必然漂移 |
| 换月三步黑屏 | 改 JSON 文件 → SSH 跑 load → 跑 extract → 跑名册 sync，漏一步就错 |
| 渠道编号洗牌 | 编号按「月目标降序」派生，目标一变编号全变，填报人刚记住就作废 |
| 管理面割裂 | 名册在 ops-web 页面管，目标靠文件+CLI，不在一个视图里 |

## 3. 目标模型：填报单元 = 一个对象，两副面孔

以「填报单元」（reporting unit）为中心实体，三类：**店铺**（渠道）、**区域**（日报）、**部门**（餐饮）。每个单元挂两组属性：

```
填报单元（店铺/区域/部门）
 ├── 权限面：负责人集合（名册 dim_report_roster）——决定「谁能填」
 └── 指标面：月目标（channel_monthly_target 快照）——决定「填多少算达标」
```

**唯一真源原则**：

1. **名册是负责人的唯一真源**。`fact_channel_store_target.owners_json` 降级为
   **名册的投影**（由名册生成，不再手工维护）——机器人在读的「谁能报哪店」
   与榜单页展示的「这店归谁」天然一致，永不漂移。
2. **目标是按月快照的指标真源**。raw `channel_monthly_target` 每发布一次就是
   一份新快照（同月重发=覆盖修订），extract 物化到 fact 供全部下游沿用。

## 4. 数据流（S2 目标态）

```
ops-web 名册页（编辑负责人/目标）
        │  点「发布月度快照」
        ▼
raw channel_monthly_target  ← responsible_person 由名册 JOIN 投影生成
        │  extract-mart --dataset channel_monthly_target（手动触发或等下批）
        ▼
fact_channel_store_target ──┬─ 渠道榜单页（MTD ÷ 月目标）
                            ├─ 渠道机器人名册源（fetch_roster_rows 已切名册表）
                            └─ 店铺编号（§6 稳定性改造后不再按月目标洗牌）
```

与 S1 的差别：目标 JSON/页面**不再携带 owners**；`sync_from_targets` 从
「事后对齐」变为「无需再跑」（名册本来就是真源）。owners_json 只是发布
快照时由系统投影出来的展示字段。

## 5. 管理面设计（去黑屏的关键一跃）

ops-web「填报名册」页升级为 **名册×指标一体视图**：

- 按渠道分组，每行 = 店铺：`目标（元，可编辑）｜负责人（增/停/删）｜启用｜备注`；
- 目标编辑与负责人编辑同页完成，改动先入「**草稿快照**」（页面态，不落 raw）；
- 页尾操作：**「发布 YYYY-MM 快照」**——把当前草稿同事务写入 raw
  `channel_monthly_target`（owners 由名册投影），随后系统自动触发
  `extract-mart --dataset channel_monthly_target`（走 ops 触发表
  `pd_ops_run_request`，复用「立即运行一次」通道），页面显示发布结果；
- 每次发布与每次负责人变更都落审计（目标发布记快照行数/合计）。

工作流变成：**页面上改 → 点发布 → 完**。无 JSON、无 SSH、无 CLI。

## 6. 编号稳定性（必须顺带解决）

现状：渠道内编号按**当月目标降序**派生（`build_roster`）。10 月目标大变
（如 TM习酒酒类旗舰店 300→470万、PDD习酒白酒专卖店 140→250万），编号
会洗牌——填报人按旧编号填报会写到别的店（**高危**）。

建议（三选一，倾向 A）：

- **A. 编号冻结**：编号改为按「首次入册顺序」固定（名册表加 `store_no`
  列，新店取 max+1），目标变化不再影响编号；
- B. 编号按**上月**目标降序（换月当月不变，次月才变，给一个月适应期）；
- C. 维持现状但换月发布时把「新旧编号对照」发群公告（运维成本最低，治标）。

## 9. 兼容与风险

- **日报区域 fail-open 不变**：统一模型只加能力，无记录的区域仍不拦截；
- **S2 切换当月的双写窗口**：名册投影上线前，`sync_from_targets` 继续
  兜底（10 月这次导入仍走 S1 路径：load → extract → sync）；
- **合计核对**：每次发布前页面显示分渠道合计与总计（对账 5480 口径），
  不一致可改后再发；
- **extract 失败**：发布走 run-request 通道，失败状态回显在定时任务页
  「最近运行」列，raw 快照本身已生效，可安全重跑。
