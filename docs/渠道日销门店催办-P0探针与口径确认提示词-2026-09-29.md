连接约定（`from common.public_data.settings import Settings; from common.public_data.db import connect`）：

## 3. 探针任务清单

### T1 通讯录能否支撑 unionId → userId

```sql
SELECT COUNT(*) AS total,
       SUM(payload_json LIKE '%%unionid%%') AS with_unionid
FROM dingtalk_org_member
WHERE sync_run_id = (SELECT sync_run_id FROM dingtalk_org_member ORDER BY synced_at DESC LIMIT 1);
```
- 输出：通讯录总人数、`payload_json` 含 `unionid` 的人数与占比，并打印 1 条样例 payload 的键列表（**只打键名，不打完整个人信息**）。
- 结论字段：`UNIONID_AVAILABLE = True/False`。

### T2 AI 表负责人携带 unionId 的比例

来源：`fact_channel_store_target.owners_json`（全店）+ 近 30 天 `fact_channel_daily_sales.responsible_person`。
- 输出：owner 条目总数、含 `unionId` 的条目数/占比、样例 3 条（只含 name + 是否有 unionId）。
- 若 owners 只有 name 没有 unionId → 直接判 Q1 走"姓名匹配"分支，`UNIONID_AVAILABLE` 无意义。

### T3 映射率测算（核心）

对每个去重后的负责人姓名，按三级链路尝试解析（逻辑同 P2 设计，探针里先算命中率即可）：
1. `unionId` → `dingtalk_org_member.payload_json.unionid` → `user_id`
2. 姓名精确匹配 `dim_robot_member`（跨 region）
3. 失败

输出三类名单（**导出 CSV 到 `tmp/`，文件名带日期，不入库**）：
- `owners_mapped.csv`：可 @ 的姓名→userId
- `owners_ambiguous.csv`：姓名匹配到多个 userId（不能 @）
- `owners_unmapped.csv`：完全无法映射（含疑似花名/离职，如 "zzz"、带空格/英文名）

计算 `AT_COVERAGE = mapped / (mapped + ambiguous + unmapped)`。

### T4 点名册覆盖率

- `A` = `fact_channel_store_target` 的门店集合（非空 `store_name`）
- `B` = 近 30 天 `fact_channel_daily_sales` 有行的门店集合
- 输出：`|A|`、`|B|`、`|A∩B|`、`B-A`（月目标表没有的新店/活跃店，按渠道计数）、`A-B`（有目标但近 30 天无数据，疑似停运/未报）
- 另统计：`store_name` 为空或空串的行数及其渠道分布（Q5，猫超式整渠道留空）

### T5 催办量级估算（最近 5 个自然日）

对每个 `business_date`（最近 5 天，含周末，用于观察节假日差异）按"A+B 并集"点名册统计：

| 日期 | 应到门店 | 有值 | 0 值 | NULL/无行=缺口 | 涉及去重负责人数 |
|---|---|---|---|---|---|

同时估算按 P2 设计的**单条消息**：@ 人数（去重后）、零销售段行数。**重点看常态是否超过 @ 上限 20**。

## 5. Go/No-Go 判定标准（探针报告必须给出结论）

| 指标 | 阈值 | 结论 |
|---|---|---|
| `AT_COVERAGE` | ≥ 90% | ✅ 直接实施 P1-P2（自动 @） |
| `AT_COVERAGE` | 60%~90% | ⚠️ 先让运维修名单（AI 表负责人统一为实名 / 补 userId 列），达标再上线；期间用"文本点名 + 抄送"降级上线 |
| `AT_COVERAGE` | < 60% | ❌ 改路线：AI 表新增"负责人 userId"列（运维可维护），映射改为直取； unacceptable 时退回"仅文本点名" |
| `UNIONID_AVAILABLE` | True 且 T2 ≥ 80% | 映射主链路用 unionId（抗同名） |
| `UNIONID_AVAILABLE` | False 或 T2 < 80% | 主链路用姓名匹配 + `aliases` 别名表消歧 |
| 点名册 `B-A`（活跃但无目标） | > 10% 应到数 | 必须上 A+B 并集；推动新建"在营门店" sheet（方案 C） |
| T5 常态 @ 人数 | > 20 | 调整 `at_limit`，或改为"按渠道汇总 + 详情链接"，避免长 @ 串 |
| T5 常态缺口门店数 | > 应到数 50% | 说明 T-1 采集过早或店铺确实大面积不报 —— 先找 1-2 家门店核实真实填报时间，再定 10:31 是否合适 |

> 最后一条尤其重要：若 T5 显示 5 天里每天都大面积缺口，不要急着上线，先人工问两家店"昨天数据一般几点填"，再回过头校准采集时刻（这是唯一可能需要推翻"10:31"的证据）。
