# 播报 × BI：口径统一设计稿

日期：2026-09-16 · 范围：`digital-ops`（机器人播报 / `common.bi_web` / `bi-react`）
输入：用户主张「**播报的内容，应该都是 BI 要看的信息，把两者结合**」
基准文档：`docs/BI建设指南.md`、`docs/bi-需求落地对照-2026-09-15.md`、`docs/bi-roadmap-2026-09-15.md`

---

## 0. 一句话结论

同意，且不是"应该"——**是现在就已经分裂了**。

播报侧已经在灰产式地实现 BI 要做的东西（库存③、仓储⑧、洗涤管家结构②），但绕开了 `mart_ops` 直连 WDT / 钉钉 AI 表，导致同一个 SKU 有三套库存口径并存。
结合的方式不是"BI 覆盖播报"，而是：**播报 = BI 指标的一种推送形态**。同一张卡，白天在群里有 markdown，晚上在看板上有图。

反过来看，这是 BI 的红利：③⑦⑧ 三个"缺数据源"的模块，播报侧其实**已经在生产跑**，把播报接入管线等于白拿三个模块的数据。

**结论**：结合的技术通路已经存在，缺的是把它从"榜单这一小块"推广到全部播报，并消掉口径分裂。

## 2. 硬证据：已经发生的口径分裂

| # | 分裂点 | 位置 A | 位置 B | 后果 |
|---|---|---|---|---|
| 1 | **库存动销窗口** | `stock_alert.py` 用 **7 天**（`num_7days/7`，可售≤7 天喊紧急） | `bi-需求落地对照` §5.1 定为 **近30天日均动销×15 天**安全库存 | 同一个 SKU，群里说"紧急补货"、看板说不缺；抽检会对不上账 |
| 2 | **同一批 SKU 两个销量口径** | `hot_items_monitor.py` 用 **近30天销量** | `stock_alert.py` 用 **近7天销量** | 热卖榜 Top15 的排名依据与隔壁预警依据不同根，业务会问"到底哪个准" |
| 3 | **渠道达成率** | `channel_report.py` 直读 AI 表「达成率」字段（对方表里算好的率） | `common.metrics` 定 `Σcompleted ÷ Σtarget`（非个人率平均） | 表里的率是对行级率取平均还是加权未知，**天然存在 melts 陷阱** |

> §2 的 #1、#2 需要业务裁决（见 §5），#3 应无条件以 `common.metrics` 为准。

## 3. 目标架构：播报 = BI 指标的推送形态

```
           ┌──────────────── 指标层（单一真源）────────────────┐
           │  common.bi_web.queries  +  derived  +  metrics   │
           └───────────────────┬───────────────────────────────┘
                               │ 同一份 rows
              ┌────────────────┴────────────────┐
              ▼                                 ▼
   ┌────── 内容层·渲染 ──────┐        ┌── 内容层·渲染 ──┐
   │ render_md(card) → 群播报 │        │ cardToCube → 图表 │
   └─────────────────────────┘        └──────────────────┘
              │                                 │
        dingtalk-gateway                   bi-react
              └──────────── 配置层：Nacos seed ─┘
                    一张卡：看图位 + 是否播 + 几点播 + @谁
```

### 3.1 三层职责（不可违背）

1. **指标层唯一**：任何播报不得自己查 WDT / AI 表算业务指标，必须调 `common.bi_web.queries` 的 `run_*`（或把它提到的 `common.metrics` 函数再封装一次）。数据源接入（WDT stock / stockout）走 `source-manifest` → raw → mart，**一次接入，双端受益**。
2. **内容层只渲染**：每个播报拆成 `take_rows()`（结构化、可单测）与 `render_md(rows)`（纯字符串）。现在 `hot_items_monitor.py` / `stock_alert.py` 是取数+拼串混写，须拆开。
3. **配置层决定播不播**：Nacos seed 的每条 `cards[]` 增加可选 `broadcast: {enabled, at_local, target, audience}`。看板加一张卡时顺手勾一下就同时上线播报，不用改代码。

### 3.2 非对称原则（重要）

**提醒/催办类不是 BI 信息**：18:30 提醒、20:00 催办、DING 属于流程动作，不进看板卡片体系。
但它们的衍生事实要进 BI：**填报率 / 填报及时率 / 口径缺失率** 属于数据质量指标，建议新增一组 `data_quality_*` 卡——这是现在 BI 完全没覆盖的空白。

## 5. 裁决记录

| # | 争议 | 选项 A | 选项 B | 状态 |
|---|---|---|---|---|
| 1 | 库存动销窗口 | 播报口径（7 天，已在生产跑很久） | BI 对照表默认（30 天×15 天，供应链公式） | ✅ **已裁决（2026-09-16）：选 B** |
| 2 | 渠道达成率取哪份 | AI 表里现成的率 | `Σcompleted÷Σtarget` | ✅ **无条件选 B**（IT 可执行）：AI 表的率需追查计算方式，确认前不进任何播报/卡片 |
| 3 | 播报是否订阅式 | 沿用 `daily_scheduler.py` 固定表 | 全部改 Nacos 编排 | ⏳ 暂不动调度器；**先统一取数层**，编排迁移放到阶段 C 与免登/权限一起做 |

### 5.1 裁决 #1 的落地约束（选 B 之后的唯一解读方式）

1. **主口径**（写进 `derived.py`，供播报与看板共用）：
   - 日均动销 = 近 **30** 天销量 ÷ 30；
   - 安全库存 = 日均动销 × **15** 天；
   - 补货点 = 日均动销 × 采购周期 + 安全库存（采购周期入 `dim_threshold`）。
2. **7 天口径不删除，降级为二级信号**：保留 `num_7days/7` 作为短周期动销，仅用于升级 severity，**不得单独决定"是否补货"**。
3. **同一张卡出唯一的 severity**，杜绝"群里一个级别、看板一个级别"：

   | 条件（主口径） | 附加条件 | severity |
   |---|---|---|
   | 可发库存 ≤ 0 且近30天有动销 | — | `p0`（已缺货） |
   | 可发库存 < 安全库存 | — | `p1`（需补货） |
   | 可发库存 < 补货点 | — | `p2`（规划补货） |
   | 可发库存 ≥ 补货点 | — | `ok` |
   | 任一 `p1`/`p2` | 且 7 天动销 > 30 天动销 × 1.5 | **上调一级**（急缺加速度） |

4. **热卖品清单不受影响**：`hot_items_monitor` 本就用"近30天销量"排名，与裁决后的主口径同源，无需改动——反而 `#2` 分裂自动消失。
5. **阈值是配置不是代码**：15 天 / 采购周期 / 1.5 倍系数一律落 `dim_threshold`，与 §6 P1 第 2 条一起做，业务改数不改代码。

## 6. 落地分期

### P0 · 先止血（不需要新增数据源）
1. `channel_report.py` 改为调 `common.bi_web.queries` 渠道卡（同源数据已在库）；
2. 达成率统一到 `common.metrics`；补 golden 用例钉死（参考 `derived_golden.json` 现有写法）；
3. **一个不改**:`daily_scheduler.py` 时刻表与 `stock_alert` 去重状态机（生产在跑，动它风险 > 收益）。

### P1 · WDT 库存入 DB（解放 ②③⑧）
1. `source-manifest.json` 加 WDT stock / 入库数据集 → raw → `fact_inventory_snapshot`；
2. 按 §5.1 落地库存口径到 `derived.py`（主口径 30 天×15 天，7 天下沉为升级信号，severity 复用现有 `p0|p1|p2|ok`）；
3. `stock_alert.py` / `hot_items_monitor.py` 取数层换掉，文案层不动。

### P2 · 配置统一 + 数据质量卡
1. seed `broadcast` 字段 + 播报渲染器注册（`render_md`）；
2. 新增 `data_quality_*` 卡（填报率 / 及时率 / 缺漏率）。

## 7. 验收标准

- **单侧改动、双侧生效**：改一次 `derived.py` 的 severity 映射，群里与看板同时变，无第二处需要手改；
- **口径对拍**：同一 SKU / 同一日期，`render_md` 的数字与看板卡 JSON 逐位一致（做法照搬 `derived_golden.json` 24 条对拍机制）；
- **回归**：`daily_scheduler.py` 五个任务 `--dry` 输出与改造前逐字一致（文案层不许动）；
- **开关有效性**：Nacos 某卡 `broadcast.enabled=false` 时，次日起该播报不出现，群内其他播报不受影响。

## 8. 风险

| 风险 | 影响 | 处置 |
|---|---|---|
| WDT 直连 → 走管线后有 T+1 延迟 | 17:00 库存预警变成昨天的数据 | 库存类先保留 `--realtime` 旁路，**同口径两条取数路径**，到期再切；或把跑批提前到 16:30 |
| 播报重构期间生产中断 | 机器人停一天 | P0 只改 `channel_report`，且新旧并存一版做输出对拍后再切；文案层零改动 |
| 口径裁决久拖不决 | P1 卡住 | P0 不依赖裁决，先落地；P1 按 §5#1 建议先行，业务确认或改数即可（与现有 `dim_threshold` 机制一致） |
