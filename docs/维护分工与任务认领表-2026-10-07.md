# 维护分工与任务认领表（2026-10-07）

> 目的：**两个人 + 两个 WorkBuddy 会话**同时维护 `digital-ops`，用一张表避免撞车。
> 配套文档：`docs/新成员接手与共同维护-提示词-2026-10-07.md`（onboarding + 拓扑 + 待办池）、
> `.codebuddy/rules/dops-maintenance.md`（自动加载的规则）。
> 表在仓库里，**靠 git 同步**；开工前必 `git pull`，动手前必先占 owner。

---

## §1 认领规则（四条，别嫌繁琐）

1. **单一 owner**：每个任务有且只有一个 owner。想做 → 把「owner」列改成自己名字 + 日期，并**立刻 commit + push**；谁先提交谁做。
2. **开工前 pull，占坑后立刻 push**：改表本身也是提交，避免两人同时改同一行产生冲突。冲突了以后提交者为准，前者重新选任务。
3. **互斥任务串行**：见 §2。互斥对象未完成前，不要开工。
4. **收工更新状态**：`待认领 / 进行中 / 阻塞 / 已完成`，并写一行结果（改了什么、验了什么）。**不留「进行中」过夜**——要么完成，要么写阻塞原因。

> 状态写「进行中」即视为**已占坑**，他人不得并行开工同一互斥组。

### 2.2 环境级互斥（时段与动作）

| 动作 | 避开 | 原因 |
|---|---|---|
| 手动跑 `sync-dingtalk` / `extract-mart` | 定时批次窗口（每日 4 批：02:00 / 08:00 / 14:00 / 20:00 北京） | 手动与定时并发会互相抢 run、制造假失败 |
| `compose up -d` 重建容器 | 榜单 08:30、提醒 18:30、催办 20:00 | 重建期间机器人不响应，正好撞业务时点会漏催 |
| 改 SG 安全组 | 他人正在改同一安全组 | 只加不删；同时改易误删他人规则 |
| 云上批量 UPDATE/DELETE | 任何 sync 在跑 | 与写入通道并发会锁表、制造脏读 |

### 2.3 分工面切分（默认按面分，不按任务抢）

- **现有维护者**：一切**生产写操作**、需要**业务裁决**的口径、涉及**钱**的事项（ECS 续费）、需运维亲手的操作。
- **新同学**：**只读巡检**、**文档与一致性校对**、**纯代码且可回滚的改动**、**测试补齐**。
- 跨面任务（如 T8）拆成「诊断（新人只读）+ 修复（维护者）」两段，各写各的结论。

## §4 每日节奏（建议，成本很低）

- **开工前**：`git pull` → 看本表 → 确认自己任务的状态还是「待认领/自己的进行中」。
- **占坑**：改 owner + 日期 → `commit + push`（只改这一行，别夹带别的改动）。
- **收工**：更新状态与一行结果 → push。跨天未完成必须写阻塞原因。
- **撞车时**：同一任务两人都要做 → 谁先 push 谁做；后者改选，或在任务下追加「协作者」而非并行开工。
