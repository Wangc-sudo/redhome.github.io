# 小易答复架构（2026-11-02）

> 背景：两张用户截图（致中和 21 天查询被护栏拒绝后推「分段跑」给用户、
> 金质合计行裸数字被连读）引出 #331-#334 四个补丁。补丁反应的架构缺陷是：
> 工具结果以**截断 JSON 字符串**在管道里流动，显示层只能事后解析、猜测
> 语义，结论/表格/引用各是补丁。本文定稿目标架构，后续优化（Skills 标准化、
> 评测集、缓存）均在此架构上推进。

## 层与单向数据流

```
理解层 focus      问句 → Focus（期间 Period / 同比 / 粒度 / 点名渠道）
取数层 executor   工具结果 payload → ResultSet（result.from_payload 唯一入口）
显示层 render     ResultSet + Period → AnswerBlock（结论卡 + 明细表 + 空态）
组装层 run_agent  候选 AnswerBlock + [[表N]] 占位符引用；LLM 只写业务解读
```

横切（不在本架构改动面）：`reply_filter` 出口治理、`kb_qa_audit` 观测、
`query_export` 导出（导出走全量快照，与显示层行过滤互不影响）。

## 三条契约

1. **数字只能来自 ResultSet**。合计、日均、极值由显示层代码计算；
   prompt 明确禁止 LLM 复述卡片数字、禁止手写 Markdown 表格。
2. **期间以理解层为准**。`render_answer` 先按 `focus.Period` 过滤行，
   结论卡与表格出自同一份过滤后行数据——「问昨天、合计跨 4 天」
   这类期间错位从机制上消除。
3. **表格与结论只能由显示层产出**。LLM 通过 `[[表N]]` 占位符选择
   相关块；未引用的块（中间探索过程）不发出；单格标量锚点在
   `from_payload` 归一化处过滤，永远进不了候选。

## 关键类型

- `result.ResultSet`：`tool / rows / total_rows`，`complete` 属性标记
  截断态——不完整结果集不出结论卡与合计（部分行求和是误导）。
- `render.summary_card`：区间 + 合计 + 日均 + 峰值/谷值；单行、不完整
  结果集不出。
- `render.render_answer`：期间过滤 → 结论卡 + 明细表（合计只在结论卡
  出现一次）。

## 与 Skills 标准化方案（2026-10-30 计划）的衔接

- `ResultSet` 是列语义声明（display/export/freshness）的挂载点：Skills
  Task 1 把 `_SQL_TABLES` 口径迁进 `query_sql/SKILL.md` 时，本架构不变；
  后续可增加 `display_columns` frontmatter，让结论卡指标选择从「列名
  推断」升级为「技能声明」。
- `query_sql` 的范围谓词/`DATE()` 禁令口径（#331）即 SKILL.md 正文内容。
