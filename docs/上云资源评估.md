### 2.3 探测证据

**Redis（域名解析 → `172.23.6.98`，与 ECS-A 同 VSwitch `vsw-bp1oeivjy3ohu002wf6hi`）**

```
# ECS-A（172.23.6.96，同 VSwitch）— 完全正常
PING1/2/3 : +PONG  +PONG  +PONG
SET       : +OK
GET       : ok
redis_version: 7.0.15     redis_mode: standalone
DBSIZE/DEL: 1 / 1
TLS       : 握手超时（说明是明文端口，非 TLS）

# ECS-B（172.28.9.236，不同 VSwitch）— 25s ×3 全部超时
try 1/2/3 -> TimeoutError
```

> **结论**：Redis 当前白名单只放行到 `172.23.6.0/24`（ECS-A 所在段）。
> ECS-B 在 `172.28.x`，未放行。Redis 是 **fail-open** 组件，备用机不配 `REDIS_URL` 即可，不影响主业务。

**踩坑记录**：首轮用 6s / 10s 超时探测时，连 ECS-A 也报超时，**是超时设太短导致的假故障**——Redis 首次建连明显超过 10s。
应用侧连接超时建议 **≥15s 或带一次重试**，否则线上会出现"能连却报超时"。

**RDS**：两台 ECS 均收到服务端主动回的握手包，含版本号 `8.4.7`，白名单已放行。

```
                 │                                                  │
  公网 ────────▶ │  ECS-A  数据面 (k区, 172.23.6.96, c7.large 2C4G)  │
  (入站仅 443)   │  ├─ docker compose（移除 mysql 服务）              │
                 │  ├─ dingtalk-gateway  [长驻·持钉钉凭据·Stream]     │
                 │  ├─ bi-web            [长驻·18080]                │
                 │  ├─ nginx 反代 (HTTPS 终止)                       │
                 │  └─ cron: sync / extract / robot / pages          │
                 │        ├──▶ RDS  MySQL 8.4.7 (k区)      ✅已通    │
                 │        ├──▶ Redis 7.0.15    (k区)      ✅已通·免密 │
                 │        └──▶ Nacos:8848 (→ ECS-B)       ⚠️需放行   │
                 │                                                  │
                 │  ECS-B  控制面 (j区, 172.28.9.236, u1 2C4G)       │
                 │  └─ Nacos 2.4.3 standalone  [长驻]                │
                 │       Docker 29.8.0 + Compose v5.5.1 已装        │
                 │       group=PIPELINES / REGIONS / BI             │
                 └──────────────────────────────────────────────────┘
```

**为什么 ECS-B 跑 Nacos：**

1. **Nacos 不碰 Redis** —— ECS-B 连不上 Redis 的短板对 Nacos 完全无影响（只用 Derby/MySQL）
2. **Docker 已装好** —— 29.8.0 + Compose v5.5.1，开箱即用；ECS-A 还得现装
3. **控制面独立** —— 业务容器全在 ECS-A，Nacos 独占 ECS-B，重启/发版互不影响
4. **内存隔离** —— Nacos JVM XMX 512m + 堆外实际常驻 1G+，ECS-A 只有 2C4G 挤不下

### 4.1 Nacos 是必需组件，不是可选项

代码层的 fail-open（Nacos 挂 → 回退 seed）是**容错设计，不是部署选项**。以下证据说明生产必须部署：

| 来源 | 原文 |
|---|---|
| `阶段4切换运行手册.md` §1 | "种子里 robotCode / conversationId / tableUrl 是**占位符**；**真实值只进 Nacos**" |
| `region_config.py` L11-12 | "真实值由运维发布到 Nacos，**不入 git**" |
| `tests/common/test_region_config.py` | `test_shipped_seed_keeps_placeholders_out_of_git`：断言种子 robotCode 以 `<` 开头 |
| `测试环境配置单.md` §10 | "机密只存在于**仓库外文件与 Nacos**" |
| `BI建设指南.md` | 核心原则"**SQL 在代码、编排在 Nacos**"；整页/整站关停靠 Nacos `enabled` |
| `pipeline_config.py` 模块头 | "the **Nacos-backed control plane**" |

> **直白说**：不发 Nacos，机器人用的是 `<占位符>` robotCode，消息发不出去。

### 4.2 Nacos 部署要点

**端口**（Nacos 2.x，安全组需放行 ECS-A → ECS-B 内网）：

| 端口 | 用途 |
|---|---|
| 8848 | HTTP API / Console（`nacos-sdk-python` 走这个） |
| 9848 | gRPC 客户端（8848 + 1000） |
| 9849 | gRPC 服务端（8848 + 1001） |

**环境变量**（ECS-A 上所有业务服务）：

```bash
# compose 里默认是容器名 nacos:8848，上云后必须改成 ECS-B 私网地址
PUBLIC_DATA_NACOS_SERVER=172.28.9.236:8848
PUBLIC_DATA_NACOS_NAMESPACE=production
PUBLIC_DATA_NACOS_GROUP=PIPELINES     # 管道服务；bi-web 固定用 BI，代码里写死
PUBLIC_DATA_NACOS_USERNAME=<设鉴权后填>
PUBLIC_DATA_NACOS_PASSWORD=<设鉴权后填>
```

> 注意 `bi_web/config.py`：`BI_GROUP = "BI"` 是**代码常量**，不读 `PUBLIC_DATA_NACOS_GROUP`。

**首次发布（照 `阶段4切换运行手册.md` §1）**：

```bash
# 1. 起 Nacos
docker compose -f docker-compose.integration.yml --profile nacos up -d nacos

# 2. 发布真实 region 值（仓库外文件，含 robotCode / openConversationId）
PUBLIC_DATA_NACOS_SERVER=172.28.9.236:8848 \
python -m common.gateway.cli publish-regions --source /仓库外/regions-prod.json

# 3. 发布管道注册表
PUBLIC_DATA_NACOS_SERVER=172.28.9.236:8848 \
python -m common.public_data.cli publish-pipelines \
  --seed docker/integration/pipelines.seed.yaml --if-missing
```

验收：Nacos Console 中 `REGIONS` 组可见 `region-hangzhou.yaml`，`robotCode` 为真值而非 `<...>`。

### 4.3 Nacos 的三个风险

**① 持久化**（最要命）：compose 里 `MODE=standalone` 用的是**内嵌 Derby**，容器销毁配置即丢失。

| 方案 | 做法 | 风险 |
|---|---|---|
| A 接 RDS | 新建 `nacos` 库，配 `SPRING_DATASOURCE_PLATFORM=mysql` | ⚠️ **Nacos 2.4.3 官方只支持 MySQL 5.7/8.0，我们的是 8.4**，驱动兼容性未验证 |
| B Derby + 数据卷 | 挂 volume 持久化 Derby 文件 | 单点，但够用 |
| C Derby + 重发 | 接受丢失，重建后重跑 `publish-regions` | 有 `regions-prod.json` 在仓库外即可恢复 |

建议 **B 起步**（挂卷），若要 A 先在测试库验证 Nacos↔MySQL 8.4 驱动。

**② 鉴权**：compose 里 `NACOS_AUTH_ENABLE=false`（无鉴权）。上云后 ECS-B:8848 在 VPC 内裸奔，且 Nacos 存着 robotCode 等真值——**必须开鉴权**，并同步设置 `PUBLIC_DATA_NACOS_USERNAME/PASSWORD`。

**③ 跨可用区延迟**：Nacos 在 j 区、bi-web 在 k 区。`bi_web/config.py` 写明：

```python
_DEFAULT_CACHE_TTL_SECONDS = 30.0
# 文档字符串：Nacos 不可达时，每次读有 ~4s 惩罚（_nav_entries 的 N+1）
```

即每 30s 刷新一次缓存，撞上网络抖动就是**每次页面渲染多 4 秒**。
缓解：把 Nacos 客户端超时调短（远小于 4s）、监控跨 AZ RTT、必要时把 Nacos 迁到 ECS-A（届时 ECS-A 需扩内存）。
